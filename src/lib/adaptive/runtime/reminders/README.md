# Requested reminder delivery

The ordinary reminder path uses the existing private account aggregate as its durable queue. Creating or snoozing a reminder writes its schedule before returning. The server maintenance worker drains due items without an open Mini App. There is no browser timer dependency.

Release is off by default. `STUDIO_REMINDER_DELIVERY=1` requires supported persistent file storage, polling bots and `STUDIO_MAINTENANCE=1`. Issuing the separate Telegram choice requires a currently confirmed interactive profile and the canonical reminder purpose/capability. It presents a versioned disclosure and requires its current, single-use server receipt before issuing a reminder-only authorization for at most 30 days. The authorization is bound to account/person/space, purpose revision/epoch, recipient revision and credential endpoint; old enabled channels have no such authority and require reconsent. Background delivery requires this authority, current reminder purpose/capability, exact agent grant and per-space inbox/reminder switches. Opening a Mini App never establishes a Telegram recipient. The manager's verified private DM must match `chat.id === from.id`, come from an approved member and bind to the credential-specific manager endpoint. Credential rotation invalidates old channel proofs.

A channel choice covers newly created reminders. Its deadline is the earliest of 30 days, purpose expiry and capability review expiry; due times at or beyond that deadline require explicit renewal before saving. Explicit renewal preserves already armed, currently permitted scheduled alerts. It never arms inbox-only, expired, cancelled or unknown alerts. Renewal refuses claimed/dispatching attempts with an explicit busy/retry message. Existing inbox-only reminders are not silently armed; explicitly snoozing one can create a new scheduled generation after channel enable. Source withdrawal, deletion, grant change, reminder authorization expiry, identity clear/replacement, disabled settings or lost Studio access prevent a send. The ordinary 12-hour interactive profile TTL does not expire this separate reminder-only authorization; same-account/person reconfirmation never extends it. Read, export, create and snooze still require current interactive confirmation. No private context/provider access follows from the background authorization. Unknown timezone and quiet windows defer a scheduled item. IANA timezone rules handle repeated/skipped DST hours. An explicit per-reminder exact-time choice can override quiet hours, but cannot override an unknown timezone or permission. Due times are absolute timestamps; the form labels device-local entry and displays the selected account timezone.

Before the one external request, the worker durably records a dispatch marker and checks recipient/Studio authority, canonical source and permission, channel/settings fingerprints, lease/expiry and quiet policy. After all awaited checks and body preparation, a final synchronous fence reads the latest committed account file through strict schema/account/permission validation and latest committed Studio file, then rechecks reservation/source/permission/recipient/settings/clock immediately before fetch. An account writer lock defers the unattempted generation; an unsupported or malformed snapshot fails closed. This supports the single-process file/polling runtime only. It does not claim distributed atomicity across OS processes, both stores or Telegram. A storage failure while persisting a deferred result remains a visible maintenance failure; an ambiguous dispatch marker never becomes permission to resend.

## Delivery evidence and failure behavior

- `claimed`: a durable 15-second lease, with no network request yet. A restart after lease expiry can safely reserve again.
- `dispatching`: durable before the request. A restart cannot determine whether Telegram received it; lease expiry becomes `unknown` and never automatically resends.
- `accepted`: a successful HTTP response with Telegram `ok:true`, positive message ID and the exact recipient chat ID. This proves API acceptance only; it does not prove device delivery or reading.
- `failed`: a recognized Telegram rejection. No automatic retry; snooze requests a new generation.
- `unknown`: timeout, network error, malformed response or contradictory HTTP/body. No automatic retry. Reviewing it records only the user's review; the provider outcome remains unknown. Explicit snooze preserves the prior receipt and requests another alert, which may duplicate an earlier ambiguous delivery.

The transport performs one guarded `sendMessage` fetch with a five-second bound, no SDK retries, generic text (`You have a reminder in Vox.`), recipient ID and optional opaque inbox reference. Reminder labels, agent names and space labels are not exported. The authenticated link requires current interactive authority and resolves only an accessible own reminder, selects its actual space and otherwise shows a generic unavailable state. Queue/ledger bounds are 100 inbox records and 500 receipts; receipts expire after 30 days. Ordinary reminders are explicit requests, separate from the proactive daily cap. Maintenance defaults to two candidates per account per pass; due time is not an exact delivery-time promise.

Telegram's documented `sendMessage` result is a Message object: [official API reference](https://core.telegram.org/bots/api#sendmessage). This adapter has no timeout reconciliation endpoint. Reconciliation is therefore an honest unknown record plus explicit user review/new intent, not fabricated provider delivery.

## Verification and evidence limits

`reminders.test.ts` exercises actual file storage, the runtime service and the Studio transport with a controlled Telegram adapter. It covers independent workers, process exits both before and after the dispatch marker, restart, signed HTTP boundaries, future reminders, snooze generations, generic projection, source/access/consent/settings/endpoint races, quiet boundaries and actual Tallinn DST dates. Transport tests cover authorization, protocol failure and no retry. Component tests cover English/Persian explicit choices and unknown-status controls.

`playwright.reminders.config.ts` runs `e2e/reminders.spec.ts` against a production build on isolated port 3106 with synthetic API fixtures and all provider credentials absent. It checks the opaque personal reminder link, EN/FA layout and explicit channel/snooze behavior. Browser results are recorded separately by the coordinating release agent. These checks do not qualify a real Telegram device, a live send, deployment, wall-clock accuracy, or measured delivery latency.

## Rollback

Keep delivery disabled and stop every scheduler/producer before restoring an older binary. Disabled mode does not seed delivery state. Once enabled, old strict schemas reject `experience.reminderDelivery` and item `delivery` fields. `removeReminderDeliveryForRollback` is a pure offline projection removing only these fields; preserve the original content-free ledger in protected storage first. It leaves schedules, labels, consent, source tombstones, rights, events and budgets untouched, and never re-arms an item. Apply under the existing file-store writer lock with an exact account scope and compare-and-swap digest. Telemetry has its own rollback projection; run both where applicable and validate the projected aggregate against the exact target schema. Never replace current rights or deletion tombstones with an old account backup. Re-enabling delivery after projection requires a fresh explicit channel choice/new reminder or snooze; stripped existing items are inbox-only.

Local source qualification (2026-10-19, `codex/vox-adaptive-runtime` working candidate based on `ee800d9`): final reminder/file/HTTP/crash/rollback/durable-authority suite **44 passed**, adapter suite **12 passed**; component and adjacent existing Experience tests also passed. TypeScript and focused ESLint checks passed. An isolated verification loaded the exact `ee800d9` full repository plus old runtime/observer schemas from Git: the raw enabled aggregate was rejected, and the combined reminder/telemetry rollback projection was accepted with authored label, permissions and event history preserved. Temporary schema copies were removed. No live account file was read or changed.

For rollback preview, invoke `pruneFileReminderDelivery({ directory: '/absolute/reviewed/adaptive-directory', accountId: 'telegram-account:<explicit-id>' })`. It returns only a digest and changed flag and never writes. Applying requires `apply:true`, `producersStopped:true` and the exact preview `expectedContentSha256`; it uses the existing file writer lock and fails if the aggregate changed. Run this only as a separately reviewed operational step after archiving the original ledger; the implementation task executed it only on synthetic temporary directories.

Durable-authority qualification additionally proves next-day delivery after actual file-adapter restart with expired interactive identity, while private snapshots remain empty and create/snooze remain denied. It covers versioned disclosure receipt expiry/invention, changed recipient during presentation, legacy-channel reconsent, no implicit renewal on same-person reconfirmation, expiry horizon, and identity-clear/purpose/grant/recipient revocation after the interactive TTL. The server endpoint is `POST experience/reminder-channel/present` followed by `PUT experience/reminder-channel` carrying `receipt` and `disclosureVersion`. Both operations are signed, same-origin, revisioned commands. The receipt is consumed when the user confirms.


## نتیجه و محدودیت‌ها

یادآور معمولی در فایل خصوصی حساب ذخیره و با زمان‌بند سرور، حتی هنگام بسته بودن برنامه، بررسی می‌شود. انتخاب تلگرام پیش‌فرض خاموش است. ابتدا متن نسخه‌دار مجوز نمایش داده می‌شود و تأیید صریح با رسید معتبر سرور، فقط برای اعلان عمومیِ یادآور در همان حساب و فضا، حداکثر ۳۰ روز مجوز می‌دهد. مجوز تا زودترین زمانِ پایان رضایت، بازبینی قابلیت یا ۳۰ روز معتبر است. انتخاب‌های قدیمی بدون این رسید خودکار ارتقا نمی‌یابند. انقضای ۱۲ ساعتهٔ ورود تعاملی این مجوز محدود را تمدید یا لغو نمی‌کند؛ خواندن جزئیات خصوصی، خروجی گرفتن، ایجاد و تعویق همچنان به تأیید جاری نیاز دارند. تأیید دوبارهٔ همان شخص نیز پایان مجوز یادآور را عقب نمی‌برد. پاک شدن هویت، تغییر حساب/شخص، پس‌گرفتن رضایت، حذف منبع، تغییر مجوز عامل یا گیرنده و چرخش کلید ربات، ارسال را متوقف می‌کند. پاک کردن هویت و سپس تأیید دوباره، مجوز قدیمی را زنده نمی‌کند.

تمدید صریح فقط اعلان‌های از قبل برنامه‌ریزی‌شده با مجوز جاری را نگه می‌دارد؛ یادآور فقط در صندوق، منقضی، لغوشده یا با نتیجهٔ نامشخص را فعال نمی‌کند. هنگام ارسال جاری، تمدید با پیام انتظار و تلاش دوباره رد می‌شود. زمان مقرر پس از پایان مجوز به تمدید نیاز دارد. ساعت سکوت با منطقهٔ زمانی معتبر و قواعد تغییر ساعت فصلی بررسی می‌شود؛ استثنای زمان دقیق فقط با انتخاب صریح همان یادآور ممکن است.

پس از تمام انتظارهای ناهمگام، وضعیت نهاییِ ثبت‌شدهٔ حساب و استودیو به‌صورت همگام، درست پیش از آغاز تنها درخواست تلگرام خوانده و مجوز، منبع، گیرنده و زمان دوباره بررسی می‌شوند. قفل نویسندهٔ حساب، تلاشِ هنوز ارسال‌نشده را به نوبت بعد می‌سپارد. فایل خراب یا ذخیره‌ساز پشتیبانی‌نشده اجازهٔ ارسال نمی‌دهد. این تضمین برای اجرای فایل/پولینگ در یک فرایند است؛ تراکنش توزیع‌شده میان چند فرایند، دو ذخیره‌ساز یا تلگرام ادعا نمی‌شود. خطای ذخیره هنگام ثبت نتیجهٔ تعویق، شکست قابل مشاهدهٔ نگه‌داری است. نتیجهٔ نامشخص هرگز خودکار دوباره ارسال نمی‌شود. پذیرش API تلگرام اثبات تحویل یا خواندن نیست. برچسب خصوصی یادآور از وکس خارج نمی‌شود.

بازگشت به نسخهٔ قدیمی پس از توقف همهٔ تولیدکننده‌ها و زمان‌بندها، نگه‌داری امن دفتر رسیدها و پاک‌سازی محدوده‌دار فیلدهای جدید با کنترل هش انجام می‌شود. پیش‌نمایش نمی‌نویسد. بازگرداندن نسخهٔ قدیمیِ کل حساب روی رضایت، حذف‌ها و حقوق جدید مجاز نیست. پاک‌سازی یادآور و تله‌متری جداست و نتیجه باید با طرح دقیق نسخهٔ مقصد اعتبارسنجی شود. یادآورهای پاک‌سازی‌شده خودکار دوباره فعال نمی‌شوند. آزمون‌ها مصنوعی‌اند؛ ارسال واقعی تلگرام، دستگاه، انتشار و تأخیر تحویل زنده تأیید نشده‌اند.
