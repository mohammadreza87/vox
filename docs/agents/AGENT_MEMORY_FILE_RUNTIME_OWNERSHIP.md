## Decision and boundary

Deliver an integrated cooperative single-host owner for the actual persistent Next Node process and original canonical FILE data directory, acquired before constructing local stores, starting pollers, generating replies or accessing authority for effects. The actual `getStudio()`/instrumentation/route composition, storage commit paths and existing production installer consume it. An unused lock helper is insufficient. No distributed lease, network filesystem, multi-process writer pool, transparent writer forwarding, extra daemon, public enable journey or new global feature flag.

The expected supported topology is one Next Node process with instrumentation and route bundles sharing one JavaScript global realm. It must be verified with an actual built synthetic Next fixture before deployment. Multiple OS workers/isolated realms are unsupported for the same original-FILE tree: the extra process refuses before storage/provider/polling work. If the actual installed Next topology requires those workers, do not install this candidate; return to root for another architecture. Environment flags and a process-local boolean do not establish this condition.

The owner is operational admission for FILE storage. It is independent of ATI availability, account enrollment and permission. First managed original-FILE startup, including ATI off, creates a permanent content-free ownership format marker before opening stores. This deliberately supersedes only ATI1's statement that startup creates no markers: startup still creates no ARC marker, enrollment, account, grant or replay control. Preserve all current configuration, archive availability, snapshot-off and ATI-off behavior. Never disable unrelated users because one account is unenrolled, missing a key, busy or stale. Healthy sole-owner ordinary users and pet/ARC2 data continue through existing paths.

Full physical erase/recreate, trusted bootstrap/admission floors after complete account removal, arbitrary restore and authority rollback remain a separate contract. This slice neither removes payloads nor treats a missing payload as fresh authorization. Preserve 32 detailed effects/account, exactly seven days from creation without refresh, four streams/enrollment rows, 4096-byte terminal state, 163840-byte reserved wrapper, 700000-byte canonical cap and all rights/pause reserves. No assistant text retention or stronger delivery promise is added.

## Persistent guard and capability

Use a new shared Node ESM implementation `scripts/studio-file-runtime-owner.mjs` and declaration `scripts/studio-file-runtime-owner.d.mts`, with thin typed Next adapter `src/lib/studio/file-runtime-owner.ts`. Runtime adapter imports the same ESM implementation; production.mjs imports its sibling script. Install copies the implementation to `<release>/studio-file-runtime-owner.mjs`, alongside the existing renamed `<release>/studio-runtime.mjs`, so the sibling import works in source and installed layouts. Next must bundle/trace the adapter import into standalone output; independent built checks prove the traced bytes and same registry behavior. No tsx/dev dependency or independently implemented TS/installer lock protocol. APIs are structural functions, never `instanceof` across route bundles.

`acquireRuntimeOwner(dataRoot, releaseIdentity, role)` returns an opaque process-local capability. Roles are `runtime` or `maintenance`; roles do not grant account authority. Root is an explicit absolute private directory, normalized through the existing permitted macOS `/tmp` and `/var` system aliases only. No symlink descendants/ancestors other than those exact system aliases. Reject root `/`, public/build locations, owner mismatch and group/other access. Validate data root owner UID matches effective UID and mode has no group/other bits; never silently chmod existing live data to pass. Bootstrap only a missing root's final directory under a validated private parent, 0700, before any store construction.

Guard is `<dataRoot>/.studio-runtime-owner-v1.lock`, an exclusively created regular file: `O_CREAT|O_EXCL|O_RDWR|O_NOFOLLOW|O_NONBLOCK`, mode0600, regular, nlink1, owner UID, bounded to2048 UTF-8 bytes. Do not use ordinary `existsSync` as acquisition, follow a link, accept FIFO/device/socket, or adopt a malformed/empty/unknown-version file. Immutable strict record fields: `version:1`, `kind:'studio-file-runtime-owner'`, `role`, `nonce` (32 random bytes as64 lowercase hex), `pid` (positive safe integer), `startedAt` (safe trusted integer milliseconds), and `release:{revision,sourceTree,buildId}` (strict existing release identity; an explicit synthetic identity is permitted only for a synthetic root). No paths, Telegram IDs, account names, keys, credentials or content in this record. PID is diagnostic; nonce and inode are identity, not permission to steal.

Write through held FD, fsync file then data-root directory before publishing the capability. Capture root FD and root identity plus lock FD identity using BigInt stats (device/inode/birthtime where available), UID/mode/nlink/size, and immutable record bytes/digest. `assertCurrent()` synchronously compares held FD, named no-follow entry and root path/FD identity, metadata and exact record bytes. It also asserts the permanent marker once installed. Detect truncation, rewrites, renames, hardlink, root substitution, owner/permissions changes and missing files. A cheap timestamp or nonce-only comparison is insufficient. Parent-component checks must run before named traversal, with a second identity check after read. Local filesystem replacement by a malicious same-UID process between synchronous syscalls cannot be excluded by JavaScript; this is cooperative supported-writer coordination, not a kernel security boundary.

The registry uses a versioned `Symbol.for('vox.studio.file-runtime-owner.v1')` on `globalThis`, keyed by canonical root identity. It holds the capability, acquisition-in-progress, state and close promise; repeated imports/HMR/route bundles join the same object. Reject differing root identity, release or role, registry version/corruption and isolated second realms. Never return an owner merely because PID matches. No per-module singleton or class identity. Capability methods cannot be recreated from record contents. Structural functions accept only the exact registered capability object/epoch/root identity authenticated by the shared registry closure (or its shared WeakSet); duck-typed callbacks, copied objects, fabricated guards and cross-realm clones refuse on a marked root. Structural means no cross-bundle instanceof, not caller-forgeable authority. For role runtime, once `draining`, `lost` or `closed`, the same process cannot reacquire that root or reset the global by retrying getStudio. Maintenance capability epochs are separately bound to a live process-local operation-guard object: after intentionally releasing one epoch before candidate start, that same still-valid operation may explicitly acquire a new maintenance epoch only after its exact candidate has exited and all expected-root/holder checks pass. This does not reopen any retired capability or runtime registry entry, and no serialized/env token can mint an operation capability. Initial acquisition failure may report closed `busy|invalid|io|unsupported` without logging filesystem/parser content. `EEXIST` always refuses; no wait-to-steal, heartbeat, TTL or PID-only cleanup.

## Drain, termination and managed release ordering

Health checks assert the current owner after awaited store reads, immediately before returning healthy; cached __voxStudio/__voxBots/revision cannot vouch for a lost capability. No holder nonce/PID or filesystem identity is exposed publicly.

Normal process state: `acquiring -> active -> draining -> closed`; any validation failure latches `lost`, never active again. Drain begins synchronously: deny new FILE writes/authority admission and Telegram effects/ingress, stop poll loops/timers/profile refresh/routines/archive/relationships/maintenance/preference tasks, abort registered I/O, prevent queued callbacks and collect task settlement. `startBots` must expose idempotent `stop():Promise<DrainResult>` and retain all current loop/refresh/maintenance/archive/background tasks, not merely close preferences. Instrumentation retains that handle and hooks SIGTERM/SIGINT once; getStudio/guest-only startup shares the same lifecycle. Enforce a bounded drain deadline with truthful incomplete result; no release of ownership if callbacks or writes can still run. SIGKILL/exit/power loss leaves guard; shutdown does not claim proof of network cancellation or power-loss durability.

For this slice choose conservative ownership release: the runtime does **not** unlink its lifetime guard while it remains a running server, including process `exit` callbacks. Managed control releases a stopped holder only after the exact runtime process has exited and supervisor cannot restart it. This avoids untracked auxiliary/exit callbacks writing after transfer. Unexpected crash-stale guard is distinct from an operation that captured the expected live holder before initiating its stop.

Existing installer lock ordering only: operation guard -> capture expected installed release/current pointer and runtime holder -> identified managed stop -> verify supervisor unloaded AND actual Node child terminated AND port no longer owned -> verify unchanged stopped-holder root/guard identities -> remove only that expected holder with directory fsync -> acquire maintenance owner -> quiesced compatibility, backup and pointer transition -> release maintenance owner -> start runtime -> verify new owner record + release/root identity + readiness. The launchd wrapper is not the Next child: record and verify both identities, actual child PID and release, not just server.pid/alive(pid)/port. PID recycling, inaccessible process identity or foreign listener yields refusal before removal/snapshot. No automatic removal based solely on kill(pid,0) returning ESRCH.

The supported stop witness is a wrapper-owned private `<productionBase>/runtime-process-v1.json`, bounded4096 bytes,0600/nlink1/no-follow, atomically written and fsynced file then parent. Strict common record: `version:1`, `kind:'studio-runtime-process'`, `spawnId` UUIDv4, `wrapperPid`, `childPid`, `startedAt`, `release` tuple, `artifactIdentity`, `rootIdentity`, `holderIdentity`, `holderDigest` and `holderNonce`; PID/time are descriptive, not sole proof. State `running` is emitted only after the actual wrapper ChildProcess object has spawned and the exact child PID/release has acquired the validated root guard; readiness requires it. A single state `exited` successor retains every immutable field and adds `previousDigest` of the captured running bytes, `exitedAt`, and exactly one of bounded exitCode or closed signal. Only the callback for **that same ChildProcess object's actual exit event** may synchronously emit/fsync exited before wrapper process.exit. This kernel-observed child relation is the stop witness; ps/alive/port observations do not mint a substitute. The installer captures the no-follow running record identity/bytes and guard before initiating managed stop, then accepts only that exact durable exited successor plus unloaded supervisor, closed listener and unchanged pointer/root/guard checks. New run must not overwrite an unretired running receipt or infer it exited; unexpected wrapper death, uncaptured holder, incomplete/changed receipt or missing exit successor fails stopped with guard retained. Never expose these fields on public health or copy this operational receipt as account authority. Receipt lifecycle/cleanup is managed under operation guard after exited identity verification, with no unbounded history or automatic live takeover.

First migration from f895 has no such receipt or root owner. Existing stop PID/port checks alone are insufficient. Before the first ownership-aware live start, release/operator must independently qualify a one-time source-defined offline process-tree/supervisor/filesystem exclusion procedure against the actual host and pin its evidence; this is currently UNAVAILABLE/HOLD. Define a bounded macOS adapter using /bin/launchctl, /bin/ps and /usr/sbin/lsof with minimized in-memory parsing only: capture the loaded label's exact resolved wrapper artifact, wrapper and actual child PID, parent relationship, OS start identity, executable and resolved cwd/expected server.js launch binding; enumerate bounded descendants, pin all observed identities, unload the supervisor, then require every captured original identity exited and listener closed under the operation guard. Maintenance acquisition/admission on an unmarked tree remains marker-free until the subsequent qualified runtime boot.

Runtime never acquires the operation guard: installer retains it while launchd's run child acquires the now-free runtime guard and health is awaited. run performs no account-store/marker/provider work before the child acquires ownership; private wrapper lifecycle metadata is separate operational state.
