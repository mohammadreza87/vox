27 October 2026. **ER1 design contract; implementation and activation are not delivered.** Source baseline `9e8752e8eb4b43fcce6303d5eb815c76618044a0`, tree `8ee228b5dcb799b3bcba4531f443063b7801b3ee`. The product lead selected the scope and engineering ceilings below; independent publication acceptance of the exact bytes is recorded by the [production program](AGENT_MEMORY_PRODUCTION_PROGRAM.md) and its external review receipts. A later implementation requires separate exact file ownership and source-work assignment. Read the [surface inventory](MEMORY_ERASURE_SURFACE_INVENTORY.md), [T1](TELEGRAM_STORAGE_DECISION_T1.md), [FRO1](AGENT_MEMORY_FILE_RUNTIME_OWNERSHIP.md), [ARC](AGENT_MEMORY_ASSISTANT_RUNTIME_CONTROL.md) and [ATI1](AGENT_MEMORY_ASSISTANT_TEXT_INTEGRATION.md) together.

## 1. Named result and claim boundary

ER1 removes one authenticated owner's **original-FILE canonical memory account**, including every row for all agents in both Work and Personal. It first closes access and removes canonical payload through an atomic closed projection, then physically unlinks the exact canonical file and fsyncs its parent. “Physical” means qualified logical filesystem removal; SSD secure erasure, backup/provider/Telegram removal and destruction of recipient copies require separate evidence.

The user operation is **Erase saved memory**, with a preview stating **Canonical memory account · All agents · Work and Personal**. It does not mean “Forget everything”, account deletion or all-product erasure. The inventory explicitly identifies retained chats, shared/legacy copies, routine/pet/connection/voice/rights data, creator personas and backups. Existing separately scoped My data controls remain distinct. No private/source text from these excluded stores may silently rehydrate the erased canonical account or become new private agent context: current-incarnation lineage is required; untraceable legacy lineage is excluded.

The qualified current-owner/member private Work-DM cohort refuses pre-confirmation sources before commands, greetings, legacy fallbacks, generation and effects. ER1 does **not** promise universal Telegram silence: existing public/group/reply-only flows may continue only when independently proven to read/use/create no canonical/private context for the affected missing/erased owner or their old-incarnation projections. Other people's independently authorized data is not erased or globally blocked. Removing membership, changing a route or moving to a public persona cannot restore erased context. “Only reply to me” does not become mandatory durable-account enrollment. Broader old-source/effect coverage remains an activation gate; an out-of-scope stateless reply is not reported as a qualified zero-POST result.

## 2. Identity and stored states

Account identity comes only from fresh manager-bot authentication, never a submitted account/person ID. Deterministic existing `personId`, a UUID, a bot credential or a valid old initData string does not prove fresh intent. ER1 adds a server-generated, nonreused 256-bit account **incarnation**, independent of account/person IDs and revision counters. Every scoped source, turn, cache/context package, callback, extraction, write and effect captures it at original work/queue creation, before awaited work, and rechecks actual committed state after waits and at the final mutation/export boundary. A callback cannot lazily bind itself to whatever incarnation happens to exist when it runs; captured work must never bind itself to a replacement incarnation.

| State | Allowed behavior |
|---|---|
| Missing | Authenticated read-only status is neutral: setup required, without claiming an erased history. Ordinary calls cannot create a canonical document. Fresh explicit bootstrap is the only creation path |
| Existing legacy-current | A validated existing account may receive a random incarnation through an existing-only, serialized migration before protected work. Preserve actual content, permissions, binding expiry, grants, revocations and existing floors; do not invent historical source time, optional enrollment or a fresh-confirmed claim |
| Active / fresh-confirmed | Canonical document plus strict versioned lifecycle control: incarnation, lifecycle revision, confirmation-acceptance time and original-source cutoff. Core eligibility, purpose/grant checks and ARC enrollment remain independent |
| ERASING | Strict payload-free projection in the same canonical path. All ordinary reads, imports, context use, extraction, generation and new effects deny. Only bounded cleanup, owner status and honest outcome refinement for already dispatched work are admitted |
| Physically absent after purge | Same admission behavior as missing/new. No hidden erased-identity registry or durable per-owner completion lookup is created. A new explicit bootstrap creates a different incarnation with no inherited content or permissions |

The active original-FILE document gains strict `memoryLifecycle` control with exactly `version:1`, `mode` (`legacy-current` or `fresh-confirmed`), `incarnation` (64 lowercase hexadecimal characters), `revision` (positive safe integer), and, only for fresh confirmation, `confirmedAt` and `sourceCutoffMs` (nonnegative safe integer milliseconds). No arbitrary metadata bag or inferred migration time is allowed. ERASING is a separate closed schema, not a fabricated normal AdaptiveDocument or a null tombstone. An unknown, malformed, busy, future-version or partial record refuses instead of becoming absence/legacy. Normal canonical transactions become existing-only; only the dedicated bootstrap capability may create a missing document.

## 3. Fresh protective authentication and one-use intent

New status/preview/challenge/confirmation routes use the manager-only trust boundary of `my-data-http.ts`; they never call `ensureMember`, try agent-owned bot tokens or initialize a missing account on GET. A dedicated `verifyMemoryAccountInitData` wrapper calls the actual `verifyBotInitData` verifier with current manager credential, **`requireSignature:true` and `maxAgeSeconds:300`**, passing the qualified ER1 trusted current time rather than using an implicit wall-clock default. HMAC and Telegram Ed25519 signature are both required; missing/invalid signature or future auth time beyond the qualified bound refuses. Existing `verifyManagerInitData` and unrelated manager/agent-auth defaults remain unchanged. Every mutation also requires trusted origin/CSRF checks, strict bounded JSON and account-scoped rate limits. Modern-client signature availability is an activation qualification gate, not a claim from synthetic fixtures. No browser body selects another account or file path.

After an explicit action, a server challenge binds action/scope/preview digest, authenticated owner and domain-separated HMAC of the authenticated session, current FRO1 owner/process generation, expected account absence or exact incarnation/revision/digest, random nonce and issue/expiry. Keep only the nonce hash server-side. Raw initData, names, text and bot tokens are excluded. The returned nonce is a capability, never placed in URLs, logs or durable files.

Challenges are personal **transient control**, held in a declared in-process map: at most **128 globally, one per owner, 120 seconds**, additionally capped by the auth deadline. Expire proactively; replace only the same owner's old challenge. Capacity refuses a new challenge without evicting/extending another owner's row or disrupting existing conversations. Clear on consume, erasure initiation, new challenge, expiry, owner drain/loss and restart. There is no persistent erased-ID registry. Owner status exposes at most pending/expiry for their own challenge; server logs/exports never expose the nonce or raw session digest. A protective cancellation clears the owner's outstanding challenge.

Confirmation acquires the actual account serialization lock, samples trusted time **t0 after validating the fresh confirmation and expected state**, then checks scope/preview, current authentication, challenge and actual absence/incarnation/revision. Atomically commit the complete new canonical document and incarnation, or close the selected current account for erase. Immediately before commit, recheck the actual owner, live one-use challenge, current expected state, time/auth/challenge deadline and original request cancellation. Consume the challenge at that final synchronous authority point; an uncertain/failed commit cannot reuse it. Reconcile actual current state through fresh authenticated status and, when appropriate, a new challenge. No automatic client retry or old confirmation replay creates another account.

Bootstrap creates ordinary defaults with all optional permissions not asked/off, no agent grants, archive attachment, ARC enrollment, reminders or remembered payload. It does not recreate an adult declaration, accept terms or reenroll delivery by inference. It establishes source admission; separate current core eligibility may still require explicit setup. A stale begin request alone has no account-creation effect; a pre-erasure confirmation capability is invalidated before closure and cannot consume after erasure/restart.

## 4. Source time, freshness and clock recovery

Engineering constants are **positive original-provider timestamp skew S = 2,000 ms** and **provider quantum Q = 1,000 ms**. A qualified time model must bound timestamp skew at source creation, including delayed/unreceived inputs; checking whether a timestamp looks future-dated only when it finally arrives is insufficient. This bound is a synthetic design requirement, not an observed Telegram/provider fact. Without independently qualified UTC/skew behavior, affected activation/admission remains held.

For fresh confirmation sampled at t0, set `sourceFloorSeconds = ceil((t0 + S + Q) / Q)` and `sourceCutoffMs = sourceFloorSeconds * Q`. Accept an initial scoped source only when its authenticated **original** `dateSeconds > sourceFloorSeconds`, its current timestamp is within the qualified time bounds, and its route, sender/private destination, incarnation and all current authority remain valid. Equality and same-second ambiguity refuse. Never substitute `edit_date`, arrival time, update ID, attempt ID or a new random identifier. Edits invalidate old sources independently of archive enrollment and cannot become fresh initial sends.

The cutoff is relative to **fresh confirmation acceptance t0**, not response time, rename/fsync completion or the durability acknowledgment. A post-t0 source created while the commit is pending may be eligible on a later independently delivered request only after bootstrap is durably active and all remaining checks pass. Messages refused while pending are not queued for automatic replay. A deadline cannot prove a blocking rename/fsync did not occur; preserve unknown/ambiguous outcomes and reconcile committed state. Do not claim that every precommit source is permanently rejected.

Durable bootstrap confirmation is not immediate source eligibility. Merely observing wall time past `sourceCutoffMs` is insufficient: a provider timestamp can still equal the floor until the next whole quantum, and negative provider/server skew is not bounded by the positive-skew rule above. Show **Fresh start confirmed** separately from **Ready / Send a new message**. The latter requires the next eligible whole provider quantum, independently qualified current clock/negative-skew bounds and separate core/reply eligibility; otherwise explain that setup is pending. Do not invent a negative-skew bound, fixed wait duration or immediate-acceptance promise. No Telegram readiness notice or automatic replay is sent.

A root-wide versioned time record holds only `version` and `highWaterMs`, with a minimized operational-control classification; the timestamp may still reveal activity. It contains no owner key, count, erased-ID membership or linkage hash. FRO1's single owner does not serialize asynchronous operations on two account locks: use one shared same-process root-time sequencer across actual Next bundles. While the account lock is held, enter its nonawaiting critical section, reread and validate the actual current time record, compare the trusted observation against the actual current high-water and publish a nondecreasing value with qualified synchronous temp/fsync/rename/parent-fsync operations. Never publish from a cached earlier value. The section cannot await an account lock or permit overlapping root-time writes; final owner/time fencing retains FRO1 ordering. Persist this observation before bootstrap commit and physical unlink. Compare same-process monotonic elapsed time with wall time to detect regression; restart requires a trusted sample not below the durable high-water plus the qualified UTC/skew condition. Missing/corrupt/regressed state on an ER1-marked root holds affected operations. This is not independent trusted UTC or nonrollback disaster authority. Whole-root restore remains offline when current time/control authority is unavailable.

Only internal lifecycle/qualification code reads this record; public metadata exposes no exact root high-water. Retain it while the root format exists and remove only on explicit whole-root decommission under the managed maintenance contract, never during per-owner erase. Preserve the actual newest record during code rollback; an old backup cannot establish its current value. No root-wide failure may expose other owners' data, and a single missing/busy account must not trigger a global refusal.

## 5. Erasure, outcome truth and finite cleanup

The scope preview names the exact canonical schema/manifest, selected current incarnation/revision and included/excluded domains before confirmation. Its closed manifest is `version:1`, `domain:'original-file-canonical-memory-account'`, `canonicalSchema:1`, `spaces:['work','personal']`, `agents:'all-canonical-agent-rows'`, `incarnation`, `revision`, `documentDigest`, `surfaceManifestVersion:1` and `surfaceManifestDigest`; digests are64 lowercase hexadecimal characters. Owner identity is server derived. A changed revision or scope requires a fresh preview/intent rather than expanding what the person approved. Erasure works with optional memory/ATI/key/enrollment switches off. Existing current legal/control dependencies remain named gates; do not invent permission to discard them.

1. Under the account lock and final FRO1/current-challenge/CAS fence, atomically replace canonical payload with the **ERASING projection**. Invalidate all the owner's outstanding bootstrap capabilities before closure; stop new scoped work and invalidate loaded contexts/jobs. This is not final physical completion.
2. The closed projection's exact fields are: `version:1`, `kind:'memory-account-erasing'`, `accountId`, `incarnation`, `revision`, `operationId`, `scopeManifestDigest`, `closedAt`, `sourceCutoffMs`, `attemptCount`, `lastAttemptAt`, `attemptDeadline`, `nextAttemptAt`, `metadataRetainUntil`, and `dispatchedOutcomes`. Account identity has the existing server-derived Telegram-account syntax; incarnation/digest are64 lowercase hexadecimal characters, operation ID is server UUIDv4, counter is0–3 and all times/revisions are safe nonnegative integers (`nextAttemptAt` is null when no automatic attempt remains). No name, declaration, permission/grant, memory, source text, archive body/locator or arbitrary diagnostic is retained. `dispatchedOutcomes` reuses the strict existing ARC `{state: DeliveryState, retainUntil}` row with at most **32** already-dispatched states, each encoded within the existing4,096-byte bound. Before retaining already-dispatched truth, use the existing ADP1 `invalidate_content` reducer with a valid current invalidation fence. It converts an in-flight `sending` state to `unknown` with `dispatch_interrupted`; directly changing a sending state to `contentEligible:false` is invalid ADP1. Keep only unexpired valid `sent`/`unknown` states with `contentEligible:false`, and cap `retainUntil` by its existing expiry and the operation metadata deadline. Existing ADP scope/binding/source/authority revision identifiers, keyed wire-evidence digests/lengths and provider receipt fields remain personal control, not content or grants. Drop undispatched generated work and terminal failed/cancelled detail. A valid reducer result that establishes terminal failure is removed without relabeling it unknown; the current ADP rule that ambiguous HTTP/provider rejection remains unknown is preserved. Do not add new arbitrary effect fields. The entire closed projection stays within **163,840 bytes**, reusing the existing ARC reservation; no separate permanent operation ledger is introduced.
3. Abort/drain local work and clear unsent buffers. During ERASING, only the same current incarnation/operation may refine an existing unexpired already-dispatched row. It cannot restore payload, grant/enroll, create a missing row, reinsert a dropped row or make content eligible. Timeout/lost response/crash remains unknown and is never resent; a valid definite terminal failure is dropped as failed detail rather than converted to unknown. Normal AdaptiveDocument/ARC sweeps cannot parse ERASING: the explicit ER1 maintenance consumer must schedule the earlier of next cleanup, next retained outcome expiry and the operation deadline, prune expired outcome rows under the same closed-operation fence, and never refresh expiry. Read-only status/export filters expired detail without writing or claiming that it was physically pruned. Expired/dropped/unlinked detail returns metadata-expired/unavailable to a late callback and cannot be reinserted. `closedAt` is the locked fresh erasure-confirmation acceptance sample, not an asserted filesystem completion time. Set closed `sourceCutoffMs` to the maximum of the rounded `closedAt + S + Q` horizon, existing ER1 cutoff and valid stronger ARC cutoff. Before purge, wait until trusted time is past this quarantine and all stronger valid existing barriers; malformed/unbounded future controls refuse instead of weakening a floor.
4. Reserve the attempt counter durably before filesystem cleanup. The existing lifecycle/runtime consumes at most **three filesystem-only attempts**: initial, no earlier than `closedAt + 5 minutes`, then no earlier than `closedAt + 60 minutes`. Each has a **30-second admission/attempt budget**, capped by the original metadata deadline. A restart claims at most one due attempt, against the same operation/incarnation/root/time authority. No generation, provider call or notification is part of cleanup. A blocking filesystem call may complete beyond its budget; do not infer that a timeout means it had no effect, issue an overlapping mutation, steal a lock or extend retention.
5. A dedicated physical-delete primitive holds the account lock and verifies the exact closed file identity/digest, operation/incarnation/revision and current owner/time. First remove and prove absence of every inventoried eligible canonical payload/closed-replacement transient for this operation, using registered exact identities and parent fsync. Then synchronously unlink the canonical file under the final fence and fsync its parent. No await or arbitrary text transformation occurs between the final authority check and invocation. Existing canonical commits can leave full-payload `<account-hash>.json.<uuid>.tmp` candidates if cleanup fails or a process crashes; an account-name prefix is candidate discovery, never deletion authority. Unknown/stale/unprovable associated temp or lock state is pending/HOLD for qualified operator recovery, not a full-purge claim, wildcard deletion, lock stripping or a new durable identity registry. Canonical absence alone is insufficient: success requires qualified absence of all included eligible payload/transients plus directory durability. Unlink/result/fsync failure is pending/unknown, not a success receipt or permission to recreate a missing operation/account from an old copy.
6. `metadataRetainUntil = closedAt + 24 hours` is fixed and never refreshed by status, retries, new sessions or lease extension. After three unsuccessful attempts, show pending and require qualified operator remediation; deadline expiry is an explicit retention breach, escalation and activation hold. It does not authorize silent indefinite retention, dropping safety controls, reopening or falsely asserting filesystem erasure. Operator/legal basis, notice and response qualification remain required before activation. A physical storage failure can make the retention target unachievable; evidence must state that failure.

After successful unlink, remove the in-memory operation/challenges/contexts and retain no per-owner server completion lookup. Drop late old-incarnation callbacks without recreating a file/control row. A user-held completion receipt may name scope and observation time and state that external effects/copies may remain; later absent status cannot falsely remember that historic operation. If the completion response is lost, a new authenticated status can truthfully establish only current canonical absence, not lost receipt identity. Erasure is not cancelled into content restoration; a subsequent deliberate bootstrap is a fresh account incarnation.

Owner export/status while ERASING includes this exact minimal control inventory, next cleanup/deadline, pending/unknown outcome classes and scope/coverage. Do not expose raw authentication/challenge secrets or inferred old content. After purge, status stays neutral. Excluded personal logs, rights rows, backups and provider copies retain their separate explicit schedules and erasure workflows.

## 6. Complete actual-path consumption and continuity

Protective edits retain their independent acknowledgment fence. Callback/media/voice/control paths with no qualified original-source proof may not borrow plain-text authority; qualify their bounded no-canonical/stateless behavior or refuse in the cohort. Do not claim voice delivery from text tests.

Every canonical repository writer, maintenance sweep, result callback, reviewed-memory acceptance, context cache and restoration path requires actual current incarnation/state and existing-only behavior. A cached complete document or an early equality comparison does not authenticate current authority. Final FILE/Telegram gates retain FRO1's ordering: owner I/O before trusted caller authority/deadline checks, then pure active latch and actual synchronous mutation/fetch invocation. No extra awaited owner or filesystem check can be inserted after the final time fence.

Existing healthy accounts use a serialized existing-only migration that validates current bytes and adds a random incarnation without changing content, consent, grants or expiry. Preserve stronger current cutoffs/revocations; do not fabricate history or automatic fresh-confirmed status. Already captured work without the new incarnation cannot be rebound. A single account's migration/busy/erasing state does not block another validated healthy account. Public/group/reply-only exceptions must prove they cannot become an alternate canonical/private-context path after membership, route or visibility changes.

Fresh bootstrap does not reattach old archives, shared/legacy projections, voice identity, grants or queues. Visible retained history remains governed separately; unknown incarnation/lineage cannot enter model context or extraction. If an adapter cannot enforce this, affected erasure activation stays held. A directory format switch or current user identity is not lineage proof.

## 7. Reader admission, migration and restoration

ER1 introduces `adaptive/memory-account-lifecycle-v1.json` with exact UTF-8 bytes `{"version":1,"kind":"memory-account-lifecycle"}\n`, `adaptive/memory-account-time-v1.json` with strict `{"version":1,"highWaterMs":<safe nonnegative integer>}` plus one trailing newline, and manifest/helper capability `supportedMemoryAccountLifecycleVersions: [1]`. Marker/time files are private0600, current UID, regular/nlink1 with no symlink/hardlink, bounded128/256 bytes respectively; read identity and exact strict schema must remain stable. The capability covers both files and active/closed account formats. Do not place an unsupported dotfile into a live namespace and assume an old reader ignores it safely. Independently test the actual frozen9e reader against marker-only, clock-only partial, empty/off, active/ERASING and post-unlink roots, plus valid older unmarked roots. The new reader must refuse malformed/unsupported/missing counterpart state even with the erase UI off and no accounts present.

First marker/time initialization is a separately qualified managed migration: operation lock, exact current runtime stop/exit, FRO1 maintenance ownership, trusted-clock/bootstrap availability preflight, durable time initialization and permanent marker publication, then account migration admission and compatible runtime start. Any partial state holds for explicit qualified reconciliation. Account cleanup never removes either marker/time record or FRO1 authority. Code may be released with new operation availability off on an unmarked root; creating the first ER1 marker requires an available qualified protective status/bootstrap journey. Once marked, availability switches cannot disable missing/ERASING/incarnation enforcement or the accepted cleanup obligation.

The first supported restoration operation is **current-authority reconciliation**, matching the existing lifecycle contract: intact current account/incarnation/authority is required; report source matches/suppression and import zero payload. Physical absence, ERASING or a replacement incarnation cannot be repaired from an old snapshot. Old grants, bindings, ARC enrollment/effects, archive pointers and source floors never become authority. Whole-root or snapshot-only disaster restoration remains offline until a separately reviewed independent current-authority/time protocol exists. An old stopped backup does not supply it. Code rollback must use a compatible reader against current data; never strip permanent markers or restore stale authority.
