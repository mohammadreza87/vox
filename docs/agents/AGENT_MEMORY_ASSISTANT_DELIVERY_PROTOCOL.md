26 October 2026. ADP1 contract frozen by product lead and independent privacy/security review against proposal SHA256 `7bb583f3287a7a324420dee0387086bae4f24990af13e8419026d62f505f83aa`. Implementation and independent source/CI qualification remain separate gates. This is an unused pure protocol, not a production ledger, activation, delivery guarantee or retention approval. The exact review and execution receipts are maintained under the agent-memory-production task artifacts. This repository contract preserves the approved fields, limits and failure semantics for future integration.

## 1. Smallest dependency-ready deliverable

Implement an **unused pure protocol/codec/reducer library**, ADP1, with synthetic qualification. It prepares the exact bytes for one private plain-text Telegram `sendMessage`, binds source/scope/attempt evidence, validates a normalized actual acceptance receipt and models conservative outcomes. It performs zero I/O, zero provider requests, zero persistence, zero retries and no scheduling. Allowed imports are zod, node:crypto for HMAC and node:util for types.isProxy; no I/O-capable dependencies, runtime imports or environment reads. Do not import it into production runtime, gateway, history, archive, stores or release-reader discovery. It does not fix the current gateway's inbound-ID substitution or current voice fallback. It supplies a reviewed prerequisite for those later changes.

This choice avoids inventing retention authority for a new durable control ledger. Neither T1's proposed 30-day job target nor the existing archive unknown-upload mechanism approves retention of per-conversation reply receipts/replay cutoffs. No new canonical fields, account byte allowance, assistant archive payload, capture eligibility, history epoch or feature flag is introduced. AM-05/AM-12 remain in progress. The artifact must be described as a source-level protocol prerequisite, never durable production assistant delivery.

Legacy unqualified behavior remains unchanged, including compact privacy's deliberate denial of old Tireh history. No backfill, historical import, model invocation, real Telegram destination, user content, provider/paid call, configuration, build or deployment is in this assignment.

## 2. Trust boundary

All inputs are caller-supplied evidence. This library validates shape, consistency and exact comparisons; it **does not authenticate a person, bot, source, clock, permission or committed claim**. Future runtime adapters must obtain a genuinely current committed canonical projection and authenticated ingress, enforce unique routing/claims transactionally, invoke the final synchronous authority check at the actual HTTP callback, and serialize result recording against newer source/deletion state. A fabricated or stale matching object cannot establish those properties.

A `private` literal is an expected scope assertion, never a private-room discovery mechanism. The future adapter must prove the destination belongs to the verified relationship owner. Creator/admin status is not owner access. Work and Personal, and distinct people/agents/containers, remain separate. A digest is an integrity comparison, not authority or identity proof. No content-bearing input or exception body may enter diagnostics.

## 3. Exact identity and metadata v1

Use strict nested schemas; every unlisted key is rejected. Integers are finite safe integers, nonnegative unless stated positive; negative zero is rejected for all numeric identity fields. Timestamps are integer Unix milliseconds. Required opaque IDs are ASCII `[A-Za-z0-9:_-]{1,128}`; no whitespace, path syntax, control characters or arbitrary Unicode. UUIDs are canonical lower-case UUIDv4. HMAC values are 64 lower-case hexadecimal characters. These are new protocol bounds, not an assertion that all existing production IDs already qualify.

`DeliveryScope` has exactly `{accountId, personId, agentId, space:'work'|'personal', containerId, kind:'private'}`. Each ID follows the opaque-ID rule. `DeliveryBinding` has exactly `{botId, destinationChatId, endpointBindingId, credentialBindingId, bindingRevision}`; Telegram bot/chat IDs are positive safe integers for this private subset; binding IDs/revision are opaque IDs, never a token or token fragment.

`DeliverySource` has exactly `{messageId, updateId, revision, occurredAt, acceptedAt}`. Message ID is positive; update ID/revision are nonnegative; timestamps are safe. `revision` is an accepted monotonic server source revision, not an inference from `edit_date`. `occurredAt <= acceptedAt`. The same logical source's later edit invalidates old preparation; **an edit does not authorize a second reply in ADP1**.

`DeliveryAuthority` has exactly `{authorityRevision, grantRevision, sourceFenceRevision, sourceFenceSequence, historyEpoch, deletionEpoch, expiresAt}`. The first three are opaque IDs; sourceFenceSequence and epochs are nonnegative integers. sourceFenceSequence is an adapter-supplied monotonic sequence for source invalidation; opaque sourceFenceRevision itself cannot establish ordering. Equality is exact across every field. No field replaces another. SourceFenceRevision must exist independently of archive capture/enrollment in any later integration.

`initialEffectKey(binding, source)` is `JSON.stringify(['adp1','telegram',botId,destinationChatId,messageId,'initial','primary-text'])`. It excludes update ID, accepted source revision, generation/attempt IDs, scopes, policy/consent epochs, endpoint/credential binding revisions and digest-key IDs. Therefore edits, key rotation, epoch changes and endpoint rebinding do not manufacture another initial effect identity. Source revisions and full scope still bind the claim and every transition. Bot replacement is a different provider stream and must not inherit authorization automatically. The future global ingress/routing adapter must reserve this key before assigning an input to a space/agent and reject moving that old initial source to another scope; pure per-record validation cannot enforce global uniqueness. Explicit regeneration/retry is excluded from v1 and needs a separately reviewed authorization/version contract.

`generationId` and `attemptId` are independent UUIDv4 values, frozen on creation. One initial effect permits **one attempt only**. A later generation UUID or attempt UUID must never substitute for the same initial effect. The pure reducer neither generates UUIDs nor issues new versions.

`DeliveryState` has exactly `{schemaVersion:1, kind:'assistant-text-delivery', effectKey, scope, binding, source, authority, generationId, attemptId, evidence, createdAt, lastTransitionAt, expiresAt, revision, phase, contentEligible, invalidatedAtFenceSequence?, outcome?}`. `evidence` has exactly `{keyId, generatedHmac, generatedUtf16Length, submittedTextHmac, submittedUtf16Length, bodyHmac, bodyBytes}`. Digests use the key described below; lengths refer to the exact strings/body used. `phase` is `generated|sending|sent|failed|cancelled|unknown`. Initial lastTransitionAt equals createdAt; every changing event sets it to expected.now and requires nondecreasing time. Initial revision is 0; successful changes increment by one and refuse overflow. `contentEligible` begins true and can only become false. It is a consistency flag, never permission to retain or use text. invalidatedAtFenceSequence is absent initially; after invalidation it is a safe integer strictly greater than the original authority.sourceFenceSequence, and contentEligible must be false. No source/reply/provider-return text, wire bytes, exception, token, URL, audio or keyboard lives in state.

Every outcome has fixed `{reason, observedAt}`. Sent additionally contains `receipt:{messageId, botId, destinationChatId, providerDateSeconds, textEvidence:'matches-submitted'|'different'|'unavailable'}`. Unknown/failed/cancelled have no receipt. `outcome` must be absent in generated/sending; present and phase-consistent otherwise. Reason codes are closed: sent=`provider_accepted`; failed=`pre_dispatch_failure`; cancelled=`pre_dispatch_denied`; unknown=`dispatch_interrupted|transport_error|http_or_provider_rejection|invalid_response|invalid_receipt|receipt_commit_unconfirmed`. No arbitrary strings. Receipt provider date is nonnegative safe seconds whose multiplication by 1,000 is safe; it is evidence only and never refreshes source/authority expiry. Outbound message ID is positive safe integer and never populated from inbound messageId.

## 4. Exact wire preparation and evidence

`prepareAssistantText({scope,binding,source,authority,generationId,attemptId,generatedText,decoratedText,keyId,evidenceKey,now,expiresAt}) -> PreparedAssistantText` validates all metadata first. `now >= source.acceptedAt`, authority expiry is strictly later than now, and `now < expiresAt <= min(authority.expiresAt, now+60_000)`. Addition now+60_000 must remain a safe integer; otherwise preparation fails. Validate expiresAt-createdAt as a safe positive integer <=60_000 on every codec read. No embedded clock or timer exists. `generatedText` and `decoratedText` are strings of 1..65,536 UTF-16 code units each. Decoration is supplied after citations/formatting; the helper does not import gateway `withSources`, append links, trim, normalize Unicode or invent fallback wording.

Prepare exactly `submittedText = decoratedText.slice(0,4096)`. Build the body with insertion order `{chat_id:binding.destinationChatId, text:submittedText}`; serialize with `JSON.stringify`; encode the **whole JSON string** with `TextEncoder`. `method` is the literal `sendMessage`; request verb `POST`, content type `application/json`. This subset supports no replyTo, keyboard, forceReply, parse_mode, silent, noPreview or protectContent options. Passing such fields fails schema validation rather than silently dropping them. Future runtime may only use this subset after explicit product approval; existing gateway options are unchanged now.

This intentionally matches the current client's UTF-16 `.slice(0,4096)` including an unpaired surrogate at the boundary. JSON.stringify escapes unpaired surrogates; the body bytes must retain that escape rather than hashing `TextEncoder(submittedText)` which would replace it. This is compatibility, not a Telegram validity guarantee. No surrogate repair or different character counting is silently introduced.

`evidenceKey` is an exactly 32-byte Uint8Array; `keyId` is an opaque ID. Use HMAC-SHA256 with domain separation: generated=`HMAC(key, UTF8(JSON.stringify(['adp1-generated',generatedText])))`; submitted=`HMAC(key, UTF8(JSON.stringify(['adp1-submitted',submittedText])))`; body=`HMAC(key, UTF8(JSON.stringify(['adp1-body',bodyJson])))`. HMAC identity never determines effect identity. Key bytes are not returned/stored/logged. Key custody/rotation/access are a later integration gate. Digests remain personal/control data.

Return a fresh detached prepared object with exactly `{initialState,generatedText,decoratedText,submittedText,bodyJson,bodyBytes,method:'sendMessage',verb:'POST',contentType:'application/json'}`. Its initialState is metadata-only; all four text strings/bytes are transient. Expose no mutable buffer alias to input key or caller state; callers changing returned transient bytes do not change state. `assertPreparedIntegrity(prepared,key) -> void` strictly validates that wrapper, requires initialState to have phase generated/revision0/contentEligibletrue/no outcome/no invalidatedAtFenceSequence/lastTransitionAt=createdAt, reparses metadata, recomputes submittedText from decoratedText.slice(0,4096), regenerates the body, and checks all lengths, exact bytes and all three HMACs including generatedText before a transition/classification; a passed object brand alone is insufficient. Generated HMAC compares the supplied generation evidence; generatedText stays transient in prepared and is absent from returned state. A state-only decoder cannot reconstruct/reverify generation text and makes no authenticity claim.

Prepared body cap is 32,768 UTF-8 bytes; one metadata state cap is 16,384 bytes in its canonical encoding. Reject oversized inputs before any partial result. Input traversal additionally rejects more than 2,048 nodes or 32 levels. Typed arrays are bounded before copying: 32,768 bytes per transient array and 32,800 bytes per input traversal (one body plus one key); metadata decoding checks its 16,384-byte cap before copying. Intrinsic byte-length and copy operations avoid caller-supplied array accessors or iterators. These are allocation guards, not durable retention or capacity. No aggregate partition, queue, persistent capacity or cache is implemented. At most one state is processed per call. State codec `encodeDeliveryState(state)` emits a fresh Uint8Array from fixed property-order canonical construction; `decodeDeliveryState(bytes)` rejects input beyond 16,384 bytes before decode, uses fatal UTF-8 and strict JSON/schema validation, validates cross-field invariants/effectKey and returns detached metadata only. Canonical decode additionally requires exact re-encode byte equality, rejecting duplicate JSON keys, whitespace/ordering variants, trailing data and noncanonical numeric spellings. No lenient unknown-version reader exists.

## 5. Receipt certainty and reducer

`classifyAssistantTextResponse(prepared, transportEvidence, response, key) -> accepted | unknown` is pure. TransportEvidence is `{method:'sendMessage', botId, credentialBindingId, endpointBindingId, attemptId, effectKey, dispatchedBodyHmac, observedAt}` from a future trusted HTTP adapter. Compare every field to the prepared claim and body. The library cannot prove that the wrapper describes an actual POST. Response is a bounded projection `{httpStatus, body}` where body is unknown JSON data, not the raw response string. Safely validate/copy response data before serialization: permit only finite JSON numbers, strings, booleans, null, arrays and local plain/null-prototype objects (Object.getPrototypeOf equals the local Object.prototype or null; cross-realm object prototypes are unsupported in v1); reject cycles, BigInt, undefined/symbol/function values, proxies, accessors, custom toJSON and non-JSON prototypes. Bound depth to32 and total value nodes to2,048, then limit the serialized response projection to65,536 UTF-8 bytes before receipt extraction. Every violation or getter/toJSON/serialization exception returns fixed unknown/invalid_response, with no body/error emission. Use node:util.types.isProxy before inspecting any object descriptors. Do not execute accessors or toJSON for normalization. Do not include it in a result/error/log.

Classifier results are exactly `{kind:'accepted',receipt:DeliveryReceipt}` or `{kind:'unknown',reason:'http_or_provider_rejection'|'invalid_response'|'invalid_receipt'}`. Malformed/oversized/non-JSON response projection or absent/nonboolean ok maps invalid_response; valid finite integer HTTP status other than200 or body.ok===false maps http_or_provider_rejection; ok===true with invalid consumed receipt fields or mismatched/malformed transportEvidence maps invalid_receipt. Response projection has exactly `{httpStatus,body}`; httpStatus is integer100..599. Validate projection/JSON shape/budget first, then transport equality, then status/ok, then consumed receipt fields. For bad prepared/key input, throw the fixed protocol error instead of classifying any provider result. Public failures never expose Zod/custom exceptions or values: `DeliveryProtocolError` carries only a closed code `shape|capacity|identity|integrity|transition|clock|expiry|revision`, with its message equal to that code.

Accepted requires HTTP 200 and exact `body.ok === true`, an object result with positive safe `message_id`, private chat with exact expected positive chat ID, and valid date seconds. Trusted bot/credential/endpoint/method/attempt/body binding comes from transportEvidence, never a guessed `from` field. If `result.from` is present it must have `id === expected botId` and `is_bot === true`; absence alone does not deny otherwise valid acceptance. Provider extensions outside the consumed receipt projection may be ignored only here, because actual Telegram messages carry extra fields. Missing/malformed consumed fields fail. If result.text is absent, textEvidence is unavailable; a string equal to submittedText yields matches-submitted; a different string yields different; a non-string present text makes the receipt invalid. Only fixed minimized receipt fields escape. Provider acceptance is not exact human display/read/heard evidence, and matches-submitted is only provider-echo equality.

All other responses are unknown. In particular, HTTP4xx/5xx, `ok:false`, rate limits, proxy errors, malformed JSON, generic TelegramApiError, socket/read/abort failures and an invalid success receipt establish no definite no-effect class. The first protocol supports **no post-dispatch failed/no-effect classifier** and no qualified automatic retry, including connect-timeout retries. A future adapter must issue a dedicated one-POST call or expose/review each attempt; the existing client's internal connect retry is not silently wrapped as one attempt. Receipt-write failure remains durable sending/unknown in a future adapter and cannot authorize resending.

`reduceDelivery(state,event,expected) -> state` is pure, immutable and does not execute effects. Expected contains exact `{stateRevision,effectKey,attemptId,scope,binding,source,authority,now}`. stateRevision is a nonnegative safe integer; effectKey is recomputed canonical identity; attemptId is UUIDv4; all snapshots use the strict types above; now is a safe timestamp. expected.authority/source/scope/binding refer to the original immutable claim, even on result recording. The final current dispatch check remains a future adapter obligation. Events are a strict discriminated union, exactly:

```ts
type DeliveryEvent =
  | {type:'begin_dispatch'; prepared:PreparedAssistantText; evidenceKey:Uint8Array}
  | {type:'pre_dispatch_failure'}
  | {type:'pre_dispatch_denied'}
  | {type:'record_response'; prepared:PreparedAssistantText; evidenceKey:Uint8Array;
       transportEvidence:TransportEvidence; response:ResponseProjection}
  | {type:'record_uncertainty'; reason:'transport_error'|'invalid_response'|'receipt_commit_unconfirmed'}
  | {type:'recover_interrupted'}
  | {type:'invalidate_content'; sourceFenceSequence:number};
```

No event takes a free normalized receipt. begin_dispatch and record_response require assertPreparedIntegrity, including exact equality of effectKey, scope, binding, source, authority, generationId, attemptId, evidence, createdAt and expiresAt to the current state. Only mutable phase/revision/lastTransitionAt/contentEligible/invalidation/outcome fields differ from initialState. record_response reclassifies the supplied response against that same prepared claim, attempt/body/method/binding and key; transportEvidence.observedAt must equal expected.now. A caller cannot swap an unbound classifier output into another attempt. Supplied transport evidence remains a trust assertion, not authenticated provider proof. Event uncertainty uses expected.now as observedAt. invalidate_content sequence is a safe integer greater than max(original authority.sourceFenceSequence, prior invalidatedAtFenceSequence); the next state stores it. Exact replay of the same invalidation sequence on already-ineligible state is a no-op. Sequence overflow refuses the transition; a lower sequence fails. A future adapter, not a numeric comparison alone, authenticates that newer fence. Every field must equal state, now must be >= state.lastTransitionAt. Only begin_dispatch requires now < expiresAt and fresh unexpired authority; failure/cancel/invalidate/recover/result recording remains possible after expiry. observedAt and providerDateSeconds remain original evidence times, independent of lastTransitionAt. Mismatches return a fixed typed error and no partial state. The expected object is explicitly untrusted until supplied by the future canonical adapter.

- generated -> sending via `begin_dispatch`, requiring prepared-integrity verification, exact supplied source/scope/binding/authority, `contentEligible===true`, and `now < expiresAt`. This returned value is only a proposed claim. Future runtime must commit it, then check that same committed revision/attempt/source/scope immediately at the actual POST; the pure library cannot grant dispatch capability.
- generated -> failed via `pre_dispatch_failure`, or -> cancelled via `pre_dispatch_denied`. Both mean this protocol never entered dispatch. No transition leaves either terminal phase and no new attempt is produced.
- sending -> sent only with a classifier-accepted normalized receipt bound to this exact attempt/effect/body, even if acceptance arrives after expiry. sending -> unknown for any listed uncertainty; restart mapping is a pure explicit `recover_interrupted` event, yielding unknown with dispatch_interrupted and no retry. The library itself cannot discover process death or persistence loss.
- unknown -> sent only upon a later valid actual acceptance receipt for that **same** attempt/effect/body, never an acknowledgement that sends or a fabricated reconciliation ID. unknown otherwise remains terminal for sending purposes. sent cannot turn failed/unknown. Recording known acceptance after authority loss is a control-only operation, never permission to use content.
- An explicit `invalidate_content` event sets contentEligible=false irreversibly without changing known effect truth. It may cancel generated before dispatch, maps sending to unknown with reason dispatch_interrupted and observedAt=expected.now, and otherwise preserves its effect phase/receipt. It requires the original exact expected claim plus the ordered sourceFenceSequence defined above; invalidation does not replace the original source/authority snapshot. A receipt arriving later can enrich that same attempt's truth while contentEligible stays false. No reducer call restores content/grants or advances a deletion/source fence.

Separate `record_result` comparison from send-authorizing checks: same original claim and adapter current record revision are mandatory, but expiry/current permission is not asserted as a condition for recording already-observed minimal effect truth. Otherwise a late accepted send would be falsely rewritten as no effect. The adapter must first apply any newer invalidation/current retention decision before returning state; the pure codec does not approve retaining control metadata after deletion. Revision CAS, content invalidation and an exact attempt fence remain mandatory on both paths. For duplicate accepted outcomes, compare the full normalized receipt (including providerDateSeconds and textEvidence), phase and reason and return the original state/outcome timestamp unchanged; a later observation time never rewrites that evidence. Duplicate identical unknown reason or cancellation/failure event is likewise a no-op preserving timestamps; conflicting receipts/terminal facts/reasons are rejected. No-op events do not advance lastTransitionAt or revision. Every changing event does advance both. Every event/wrapper is strict: absent/extra/phase-inapplicable fields fail; evidenceKey must have exactly32 bytes and prepared wrappers have only their listed fields. There is no reset, replace-claim, sending->generated, retry, resend or automatic pruning API.
