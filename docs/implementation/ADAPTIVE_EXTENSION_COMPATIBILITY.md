# Adaptive extension release compatibility

20 October 2026. Release admission reads actual persisted extension metadata in addition to the canonical/control/projection marker. Build manifests already copy the exported `ADAPTIVE_RELEASE_CAPABILITIES`; this change adds `supportedObserverClientExperienceVersions: [1]`, `supportedRightsLedgerVersions: [1, 2]`, and `supportedExperimentLedgerSchemas: [1]`.

| Persisted state | Required release capability |
|---|---|
| Observer `corrections` property, even empty; `clientExperienceVersion: 1` / `text_rendered` event; or projection `clientExperience.version: 1` | Observer client experience version 1 |
| Rights account ledger `version: 2`, even empty | Rights ledger version 2 |
| Controlled experiments `schemaVersion: 1` ledger, even empty/off | Experiment ledger schema 1 |

Absent extensions preserve the previous baseline admission. Rights version 1 stays compatible with the previous reader. Unknown versions, malformed declared capabilities and damaged existing metadata never fall back to an old format. Admission makes no data conversions, policy/configuration changes, account writes or snapshot restoration.

The scanner follows the runtime's active layouts: legacy `adaptive/<sha256-account>.json`; managed SQLite `adaptive.managed/stores/<marker.store>` using read-only, query-only metadata SQL; and managed FILE `head.json` references into `records`, including prepared FILE authority projection lineage. SQLite returns account identity/version and observer metadata to JavaScript, not canonical source bodies. FILE JSON is necessarily read locally to inspect its observer envelope and verify published digests; nothing is logged. Rights are under `rights-intake/v1/<sha256-account>.json`, and experiments under `controlled-experiments/v1/ledger.json`. The recognized rights clock sidecar is checked separately.

Application symlinks, hard-linked input files, corrupt/unknown envelopes, mixed identities, unavailable dependencies/stores, busy or foreign layouts and oversized inputs deny with one generic content-free error. Reads use no-follow descriptors and bounded buffers. Limits are 10,000 accounts, 700 KB per canonical account, 64 KB per rights ledger, 2 MB per experiment ledger, 4 MB per managed FILE head, and 64 MB aggregate inspected data; the SQLite backing file is capped at 1 GB and sidecars at 64 MB. This is deliberately bounded structural metadata admission, not a replacement for runtime schema validation, canonical authorization, semantic ledger validation or a full SQLite integrity check. Larger qualified deployments need a separately reviewed scanner bound.

SQLite admission uses the existing native dependency in read-only mode and does not checkpoint, migrate or initialize a database. SQLite may use its normal WAL shared-memory synchronization; canonical and WAL bytes are unchanged in the local WAL test. Concurrent changes across stores do not form one atomic snapshot. Existing `studio-production.mjs` install and rollback call admission before provider/service actions, then repeat it after the service stops before taking a backup or changing the release pointer. If state changes between those gates, the later gate must reject the incompatible release. The existing install failure path also checks compatibility before returning to a prior release. A prior binary is admitted against current data; old account/ledger snapshots are never restored to force compatibility.

Local synthetic evidence: `node --test scripts/studio-adaptive-compatibility.test.mjs` covers baseline and all extension-bearing layouts, current manifest acceptance, extension-unaware rejection, empty v2/off ledgers, published FILE digests/projections, malformed metadata, unsafe/oversized input, read-only WAL behavior and generic canary-free errors. Actual install/rollback CLI fixtures for each extension reject before any network, launchctl, backup/release-directory creation or current-pointer change. The fixture first proves that the same stored state is admitted by current capabilities, preventing a missing native dependency or broken structural fixture from masquerading as an extension refusal. Post-stop admission remains the existing CLI control path; no live service, provider, production data or deployment was exercised.
