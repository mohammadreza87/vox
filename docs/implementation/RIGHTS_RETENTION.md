# Rights ledger retention / نگهداری دفتر درخواست‌ها

VOX-056 RI2 implementation candidate, 20 October 2026. Awaiting independent acceptance. This completes a bounded local tracking-record workflow; it does not complete legal rights fulfillment or authorize activation. Production, configuration, providers and private data were untouched. Read with [RI1 intake](RIGHTS_INTAKE.md), [QA and release](QA_AND_RELEASE.md) and [privacy requirements](PRIVACY_AND_CONSENT.md).

## Reviewed policy and operator workflow

An active strict `STUDIO_RIGHTS_POLICY_JSON` can now include `retentionOperations: { terminalRetentionMs, continuityRetentionMs }`. Both are explicit positive safe integer millisecond durations with overflow rejection. There are no default legal or retention durations. Its existing review owner/reference, expiry, operator allowlist and copy hashes bind the whole policy. RI2 requires `rights-intake-ri2-v1` and the hashes of the actual JSON-serialized EN/FA copy; an old approval cannot silently authorize changed wording. Missing retention approval exposes no retention controls and returns `rights_retention_policy_unavailable` for mutations.

The current owner/superadmin must also remain on the privacy allowlist. Open the Privacy operations queue, refresh the current account page and choose **Reassess using reviewed retention policy**. This action remains available when reached record review dates block ordinary intake/actions. It requires signed current authentication, same-origin bounded JSON, a fresh encrypted operator/policy/account/space handle, expected request revision and expected policy revision. Authority, policy, handle expiry and monotonic server time are checked again at commit and response. Mutations are not automatically retried. Lost confirmation requires a queue refresh.

Reassessment records a bounded operator audit entry and advances the request revision. For unresolved requests it sets the next review to the current server time plus the reviewed review interval. It preserves the request state, reason, coverage, intake binding and legal deadline. A new policy alone does not rewrite stored dates. The operator must review every affected record; no sweep closes unresolved requests. Audit capacity is 32 entries: exhaustion fails explicitly and requires a separately reviewed continuity/migration procedure; entries are never evicted to make room.

New records bind `auditRetainUntil` from their admission policy. Closing a request under RI2 retention approval also binds `terminalRetainUntil` from closure time. The only terminal state is **closed without fulfillment**. Export prepared, waiting requester and operator pending remain unresolved. A new shorter policy cannot lower the recorded floors. An explicit reassessment can recalculate them under the currently reviewed policy; the audit records its policy revision. A legacy record without either bound floor must be explicitly reassessed before purge is available.

For a closed request the queue shows the earliest eligible purge, using the maximum of its recorded review/expiry, recorded audit/terminal floors, admission time plus the current reviewed audit term, and actual closure time plus the current reviewed terminal term. **Purge expired closed request metadata** requires a separate destructive confirmation and a second authenticated CAS command. It removes only this rights request's full metadata and audit, in the same atomic account transaction that writes minimal continuity. It does not delete account memory, exports, canonical records, provider data or backups and never reports fulfillment.

## Continuity, bounds and status

The remaining per-account tombstone contains only request UUID, Work/Personal scope, final request revision, purge time and continuity expiry. The account partition is retained; the tombstone is minimized metadata, not anonymous data. No kind, reason, legal deadline, locale, export projection or audit actor survives in the tombstone. Existing retained event IDs/fingerprints and the purge receipt remain to reject conflicting reuse. Their action label and timestamp are replaced with the common purged-record label/time, and their revision with the final revision; the old action timeline is removed. All receipts for that purged record are kept to the same horizon: the later of the explicitly reviewed continuity term and all currently retained command receipt expiries. This deliberate policy-driven preservation prevents an earlier create receipt expiring before its tombstone.

During that horizon, exact requester/create replays return authenticated `410 rights_record_expired`; semantic collisions return `409`. A repeated authorized purge returns current minimized outcome without resurrecting detail. Replaying reassessment after purge returns `purged`, never a historical request projection. A retained request reference from another account or space grants no access and returns `404`. The account Privacy panel shows the reference and bounded continuity expiry in EN/FA. The operator refresh drops purged detail from its queue. All responses remain no-store/no-referrer.

Continuity is finite. Event IDs whose receipts expired **before** purge cannot be reconstructed. Once the recorded continuity horizon expires, the reference becomes `404`; a subsequent deliberate command using an expired create event ID can create a new metadata-only request under current policy. This is not restoration of removed content. There is no indefinite deduplication claim. Expired continuity is hidden on reads and physically removed only during a later authorized transaction. Account partition and monotonic clock are not automatically deleted, including when empty. No unattended scheduler is added; the operator owns queue paging and prompt handling of due records.

Bounds remain 20 open/100 full records, 128 receipts and 64 KiB per account; RI2 adds at most 128 tombstones. Capacity, full audit, storage contention, malformed storage and clock regression fail closed, preserving unresolved evidence. Queue enumeration still returns one account page at a time and is not an indexed global queue.

## Version handling and rollback

Request records, action bodies and clock sidecars retain their existing version. Account ledger **version 2** adds tombstones and accepts the new audit action/floors. RI2 strictly validates original version-1 ledgers and projects them into v2 in memory without rewriting on read. **Every subsequent successful account ledger mutation, including an ordinary intake mutation without retentionOperations, writes v2.** Unknown versions and malformed mixed shapes fail closed. Original RI1 binaries refuse v2 ledgers; deployment rollback to RI1 therefore cannot serve current rights status.

Before enabling RI2, retain a tested RI2-capable status/operator service and the current rights directory/key as the rollback continuity path. Disable new admissions through reviewed policy if needed, preserve current ledgers, and use that service to authenticate requesters, show current references/status and let currently authorized operators reassess/purge under a valid reviewed policy. If the service cannot run, the privacy operator must handle references through the confirmed privacy channel while preserving the current ledger and clock for controlled recovery. Never restore an older ledger, resurrect purged detail, reset the monotonic clock, delete a live clock lock, or downgrade schemas by deleting tombstones. Clock-lock recovery retains the explicit stopped-writer inspection/reconciliation procedure in RI1. No production migration or rollback was executed here.

## Candidate verification and remaining gates

Synthetic local suites cover review recovery, deadline preservation, unresolved-purge refusal, admission/audit/closure floors, explicit policy shortening review, expiry boundaries, concurrent idempotence, retained create replay, collision, restart, finite continuity cleanup, account/space isolation, legacy read/mutation upgrade, operator loss at commit, strict signed HTTP/origin/schema handling, and EN/FA controls/confirmation/unknown-response behavior. The independent reviewer must evaluate the exact committed candidate and select additional failure checks; author tests are not acceptance.

Public activation still requires reviewed legal durations and wording, privacy-owner approval, operator staffing/procedures, topology qualification and independent release gates. Provider acknowledgments, backups, no-account identity verification, delegates, actual erasure/restriction, jurisdiction extensions, fully verified delivery and physical-device qualification remain unavailable. This is source and synthetic-local evidence only; no CI, deployment or legal approval is claimed.

## فارسی

این نسخهٔ RI2 از VOX-056 هنوز منتظر پذیرش مستقل است و فقط گردش کار محدود نگهداری سابقهٔ پیگیری را پیاده می‌کند. هیچ سیاست، کلید، محیط اصلی، ارائه‌دهنده یا دادهٔ خصوصی تغییر نکرده است. تکمیل حقوق قانونی کاربر ادعا نمی‌شود.

سیاست بررسی‌شده می‌تواند بخش صریح `retentionOperations` با دو مدت مثبت `terminalRetentionMs` و `continuityRetentionMs` داشته باشد. هیچ مدت قانونی یا نگهداری پیش‌فرض وجود ندارد. نسخهٔ متن `rights-intake-ri2-v1` و هش واقعی متن انگلیسی و فارسی باید دوباره تأیید شوند. نبود این بخش، عملیات نگهداری را غیرفعال می‌کند.

اپراتور باید هم مالک/ابرمدیر فعلی و هم عضو فهرست صریح حریم خصوصی باشد. پس از تازه‌سازی صف، «بازبینی با سیاست نگهداری بررسی‌شده» حتی وقتی پذیرش عادی به علت رسیدن زمان بازبینی متوقف است، قابل اجراست. فرمان به احراز فعلی، مبدأ یکسان، شمارهٔ نسخهٔ درخواست و سیاست و دستگیرهٔ رمز‌شدهٔ معتبر نیاز دارد؛ این موارد هنگام ثبت نیز دوباره بررسی می‌شوند. فرمان خودکار تکرار نمی‌شود و پاسخ نامشخص به تازه‌سازی نیاز دارد.

بازبینی برای درخواست باز فقط زمان بررسی بعدی و سابقهٔ اپراتور را ثبت می‌کند؛ وضعیت، دلیل، پوشش و مهلت قانونی را تغییر نمی‌دهد. درخواست حل‌نشده هرگز پاک نمی‌شود. فقط وضعیت «بسته‌شده بدون انجام» پایانی است؛ آماده‌شدن خروجی محلی به معنی پایان نیست. سیاست کوتاه‌تر به‌تنهایی حداقل زمان ثبت‌شدهٔ نگهداری سابقه و زمان پس از بسته‌شدن را کاهش نمی‌دهد. تغییر این زمان‌ها فقط با بازبینی صریح تحت سیاست فعلی انجام می‌شود. سابقهٔ قدیمی بدون زمان‌های متصل‌شده ابتدا به بازبینی صریح نیاز دارد.

پاک‌سازی پس از رسیدن همهٔ زمان‌های لازم و با تأیید جداگانهٔ مخرب ممکن است. این کار فقط فراداده و سابقهٔ همان درخواست را در تراکنش اتمی حذف می‌کند؛ دادهٔ حساب، ارائه‌دهنده، پشتیبان یا خروجی را حذف نمی‌کند و انجام درخواست را اعلام نمی‌کند. حداقل اطلاعات باقی‌مانده شامل شمارهٔ درخواست، فضای کاری/شخصی، نسخهٔ نهایی، زمان پاک‌سازی و زمان پایان جلوگیری از تکرار است. رسیدهای هنوز معتبر همان درخواست تا همان زمان حفظ می‌شوند. این اطلاعات حداقلی همچنان در بخش حساب نگهداری می‌شود و ناشناس نیست.

در این بازه تکرار دقیق فرمان قدیمی درخواست‌کننده، وضعیت احرازشدهٔ `410 rights_record_expired` می‌دهد و تعارض فرمان `409` است. حساب یا فضای دیگر `404` می‌گیرد. صفحهٔ کاربر به انگلیسی و فارسی شماره و پایان این بازه را نشان می‌دهد؛ تازه‌سازی صف اپراتور جزئیات حذف‌شده را کنار می‌گذارد. پس از پایان بازه، شماره `404` می‌شود. رسیدهایی که پیش از پاک‌سازی منقضی شده‌اند قابل بازسازی نیستند؛ جلوگیری از تکرار دائمی ادعا نمی‌شود. استفادهٔ عمدی از شناسهٔ فرمان ایجادِ منقضی می‌تواند تحت سیاست فعلی درخواست تازه‌ای فقط با فراداده بسازد، نه محتوای حذف‌شده. حذف فیزیکی اطلاعات جلوگیری از تکرارِ منقضی فقط در تراکنش مجاز بعدی است. زمان سرور و بخش حساب خودکار حذف نمی‌شوند و زمان‌بند خودکار اضافه نشده است.

حدود ۲۰ درخواست باز، ۱۰۰ سابقه، ۱۲۸ رسید، ۱۲۸ نشانگر حداقلی و ۶۴ کیلوبایت برای هر حساب اعمال می‌شود. سابقهٔ هر درخواست حداکثر ۳۲ ورودی دارد؛ پرشدن ظرفیت، اختلال ذخیره‌سازی، کاهش ساعت یا سیاست نامعتبر باعث توقف امن می‌شود، نه حذف شواهد حل‌نشده.

دفتر حساب نسخهٔ ۲ است. خواندن نسخهٔ ۱ آن را روی دیسک بازنویسی نمی‌کند، اما هر ثبت موفق بعدی، حتی ثبت عادی بدون عملیات نگهداری، نسخهٔ ۲ می‌نویسد. برنامهٔ قدیمی RI1 نسخهٔ ۲ را نمی‌خواند. بازگشت باید سرویس سازگار با RI2 برای وضعیت و پیگیری اپراتور و دفتر و کلید فعلی را حفظ کند؛ بازیابی دفتر قدیمی، حذف نشانگرها برای کاهش نسخه، برگرداندن جزئیات پاک‌شده، تنظیم مجدد ساعت یا حذف قفل زنده مجاز نیست. اگر سرویس اجرا نشود، اپراتور باید از کانال تأییدشدهٔ حریم خصوصی پیگیری کند و وضعیت فعلی را برای بازیابی کنترل‌شده حفظ کند.

شواهد این نامزد فقط آزمون‌های محلی مصنوعی‌اند. پذیرش مستقل، سیاست و مدت‌های حقوقی، متن نهایی، عملیات اپراتور، بررسی محیط استقرار و دستگاه واقعی هنوز گیت جداگانه‌اند. نماینده، تأیید فرد بدون حساب، حذف سراسری، محدودسازی رسمی، ارائه‌دهندگان، پشتیبان‌ها و تحویل تأییدشده تکمیل نشده‌اند.
