## Public flow and assurance

`/privacy` works without an account. EN/FA, RTL, keyboard labels, user zoom, a no-JavaScript contact fallback and full-document navigation are supported. With reviewed synthetic/local configuration, a visitor chooses only a request kind and Work/Personal/unknown context, prepares a recovery code, deliberately preserves it, submits, and checks current metadata. A fresh browser requires manual reference/code entry. A request can be closed only **without fulfillment**, with a second explicit confirmation. A lost response is unknown: the UI keeps the code in memory, blocks automatic resend and asks for deliberate status refresh. Opening a tracking request does not erase/correct/restrict data, withdraw consent or stop processing.

The server generates a UUID reference and random 256-bit recovery credential. A short-lived keyed admission ticket binds the digest, reference, exact reviewed policy and expiry; a caller cannot replace it with a weak credential. Minting creates no request row or credential record (only the monotonic clock can advance). A stored keyed digest establishes control of the tracking request only. It does **not** establish natural-person identity, contact-address control, account access or a delegation. No contact field, email/provider adapter, identity document, recording, transcript, raw free text, account lookup/link or private export is present. Operators cannot recover or replace a lost credential. No fulfillment state exists. Legal deadlines remain explicitly unresolved; locale, context and network headers do not infer jurisdiction.

Credentials/tickets travel only in no-store JSON responses and POST bodies, never URLs, logging, analytics, localStorage/sessionStorage, an automatic clipboard write or a query cache. The public page bypasses legacy Firebase/auth/chat/theme stores, Telegram SDK startup and client Sentry initialization. Guest API events/bodies are dropped from error and transaction collection; guest URLs do not create client tracing spans. Public entry/exit uses ordinary document anchors so a prior SDK/replay session does not carry across. The root theme script uses system preference on `/privacy`, without storage reads/writes. Other routes wait for SDK load/error or an eight-second fallback; legacy providers load lazily afterward. The guest runtime never calls `getStudio` or imports the generic provider/router runtime. It reads only bounded committed operator membership from the configured Studio state.

## Explicit configuration and authority

Absent configuration keeps online admission off and offers info@joyixir.com. A dedicated 32-byte `STUDIO_GUEST_RIGHTS_KEY_BASE64`, absolute `STUDIO_DATA_DIR`, local file storage and `STUDIO_GUEST_RIGHTS_POLICY_JSON` are required. Serverless/public-URL/foreign topology is unsupported. The strict version-1 policy declares `single_persistent_process`, `request_credential_only`, reviewer/reference, validity window, supported kinds, current privacy operator IDs, `guest-rights-gi1-v1` and exact SHA256 hashes of JSON-serialized EN/FA copy. It supplies draft/operation lifetimes, admission window/caps and every review/audit/terminal/continuity/receipt duration. There are **no legal or retention defaults**. Fixture policies are synthetic and are not activation approvals.

`admissionEnabled: false` blocks only new drafts/admissions. Existing credential status remains readable with the same key even if admission or policy is unavailable/expired. Current valid policy plus signed current owner/superadmin membership **and** its operator allowlist are required for queue/actions/retention; these remain available under a current policy with admission disabled. Operator handles bind request/revision/operator/policy/expiry. Final signed-session, committed membership and policy checks guard writes and responses. Removal, expiry, stale revision/handle, corruption, unsupported topology, capacity and clock regression fail closed. Requester status/close is credential-scoped, not account-authenticated. Unknown/mismatched credentials return the same404; correct credentials see410 only while their purged record's continuity is retained.

## Separate durable layout and retention

GI1 does not change the RI2 account ledger. Its separate `guest-rights/v1/<sha256("guest-rights-ledger:v1")>.json` contains schemaVersion1, a key-continuity marker, monotonic observation, durable admission window/counter, requests, bounded receipts and tombstones. The existing hardened file/clock primitive is reused; it now implements the storage interface directly rather than inheriting a generic module that imports Firebase. No schema, clock algorithm or RI1/RI2 retention behavior is changed by that refactor. `.clock-v1.json` is separate and durable. Owner-only/no-follow files, writer locking, bounded reads, fsync and atomic rename are retained. Status can advance the clock. Never reset it or delete a live/interrupted lock; use the RI1 stopped-writer inspection/reconciliation procedure.

Hard maxima: 100 full records, 20 unresolved records, 128 receipts/tombstones, 32 audit rows per record and64KiB aggregate ledger; reviewed policy can lower admission bounds. Reaching any bound refuses work, rather than evicting unresolved evidence. Global process ingress limits bound drafts/status attempts without retaining client IP identity; the reviewed admission window/count persists across restart. This is bounded abuse handling, not proven public anti-spam or distributed-DoS protection. A capacity attack can deny new admission; operational/public exposure needs independent qualification.

Admission binds `auditUntil`; closure binds `terminalUntil`. Later policy shortening does not change either floor. Explicit current-operator CAS reassessment records a new audit entry and may recalculate floors under the reviewed current policy. Purge is explicit and only for closed_unfulfilled records after both floors. Received, under review, awaiting requester and operator pending remain unresolved regardless of age. Purge removes only guest tracking detail/audit, not account/provider/backup data and not a fulfilled right. It atomically retains the credential digest, reference, last revision and continuity timestamps plus valid receipts. Continuity ends no earlier than existing retained receipts or the new purge receipt’s full reviewed receipt duration measured from actual purge time. Current authenticated410 becomes404 after that finite horizon; perpetual replay prevention is not claimed. Expired receipt/tombstone cleanup occurs only in a later successful authorized mutation; no scheduler or unresolved auto-purge exists.

The key-continuity marker rejects a replacement key for any retained ledger. Missing/replaced keys never initialize/reset it or enable recovery/account linking. Keep the exact key and current ledger/clock protected together across releases. Automatic rotation/recovery is **not implemented**. A rotation requires a separately reviewed quiesced migration/continuity plan and proof that existing credentials/status/retention remain usable; do not replace the key to force a blank start. Losing a requester code is not recoverable by an operator or by signing into an account.

## HTTP and release boundary

Public GET `/api/guest-rights` returns only policy availability/kinds. Same-origin bounded JSON POST routes `draft`, `requests`, `status`, `close` carry private credentials only in bodies. Signed operator GET `operations/requests` and POST `operations/actions` expose minimized metadata and CAS actions; no private account data or fulfilled outcome. Every guest query string is refused. The dedicated runtime validates current committed membership without starting bots, providers or Firebase. The server-configured STUDIO_WEBAPP_URL selects the trusted public origin behind a reverse proxy; it must be HTTPS with the /studio path and no credentials/query/fragment. HTTP is allowed only for explicit local loopback fixtures. Invalid configuration fails closed; Host and forwarding headers never grant origin authority. Missing configuration retains strict request-URL origin equality. Errors are content-free; responses are no-store/no-referrer. UI caching/retries are disabled.

Release manifests declare `supportedGuestRightsLedgerSchemas: [1]`. The installer scans this exact namespace and clock, and refuses an unaware candidate once a guest ledger exists, including empty or admission-disabled ledgers. Unknown versions/malformed layouts refuse; runtime schema/authority validation remains authoritative. Preserve a GI1-capable status/retention service, key, current ledger and clock for rollback continuity. Never restore an old ledger or remove tombstones to make an old release start. No production activation, deployment, live messages, real email/provider operations or legal approval were performed.

Author suites and the compiled fixture are separate from independent acceptance. `playwright.guest-rights.config.ts` starts fresh copied standalone runtimes with synthetic policy/key/operator metadata, explicit sanitized environments and denied outbound server transports. Guest journeys use actual compiled HTTP; only external browser traffic/SDK startup diagnostics are blocked or stubbed. Trace capture is off to avoid persisting credential bodies. EN/FA desktop/mobile initial and submitted screenshots keep recovery credentials hidden. Both root and standalone BUILD_ID values must match. A plain CI Next build without studio-release.json records Git source revision/tree with an explicit next-build-source-binding label; it neither creates a release manifest nor qualifies install admission. Evidence and copied fixture runtimes can be retained through GUEST_EVIDENCE_DIR and GUEST_RUNTIME_DIR. Compiled result and independent acceptance must be bound to their exact source/build receipts before release.

## فارسی

این نسخهٔ GI1 فقط پیگیری محلی درخواست مهمان را پیاده می‌کند؛ پذیرش مستقل، فعال‌سازی عمومی و تکمیل VOX-056 یا حقوق قانونی ادعا نمی‌شود. صفحهٔ `/privacy` بدون حساب، به انگلیسی و فارسی و با راست‌به‌چپ کار می‌کند. در نبود سیاست و کلید بررسی‌شده، راه تماس info@joyixir.com نمایش داده می‌شود. متن حقوقی، مدت‌ها، عملیات صندوق تماس، میزبانی، حفاظت عمومی در برابر سوءاستفاده و دستگاه واقعی همچنان نیازمند تأیید جداگانه‌اند.

کاربر فقط نوع درخواست و زمینهٔ کاری/شخصی/نامشخص را انتخاب می‌کند. پیش از ارسال باید شماره و کد تصادفی۲۵۶بیتی را خصوصی نگه دارد. سرور فقط چکیدهٔ کلیددار کد را نگه می‌دارد. کد فقط کنترل همین پیگیری است، نه تأیید هویت فرد، نشانی تماس، نمایندگی یا دسترسی به حساب. هیچ مدرک هویتی، نشانی تماس، متن آزاد، پیام خصوصی، ضبط صدا، اتصال حساب یا خروجی خصوصی دریافت یا ایجاد نمی‌شود. اپراتور نمی‌تواند کد گم‌شده را بازیابی یا جایگزین کند. مهلت قانونی نامشخص می‌ماند. ارسال یا بستن پیگیری هیچ داده‌ای را حذف نمی‌کند، رضایت را تغییر نمی‌دهد و انجام حق قانونی نیست.

کد و بلیت فقط در بدنهٔ POST و پاسخ بدون کش قرار دارند؛ در نشانی، گزارش، تحلیل، حافظهٔ ماندگار مرورگر یا کلیپ‌بورد خودکار ذخیره نمی‌شوند. مرورگر تازه نیازمند ورود دستی شماره و کد است. پاسخ گم‌شده نتیجهٔ نامشخص دارد؛ ارسال خودکار تکرار نمی‌شود و کاربر باید وضعیت فعلی را تازه‌سازی کند. صفحهٔ مهمان SDK تلگرام، احراز هویت/فروشگاه‌های قدیمی و Sentry مرورگر را راه‌اندازی نمی‌کند. ورود و خروج صفحه یک سند تازه بار می‌کند. کدهای بازیابی در تصاویر آزمون پنهان می‌مانند.

سیاست جداگانه و پیش‌فرض خاموش، کلید۳۲بایتی و محیط تک‌پردازهٔ پایدار لازم است. متن دقیق هر دو زبان، مدت‌ها، بازه و سقف پذیرش و فهرست اپراتورها باید بررسی شوند؛ مدت قانونی پیش‌فرضی وجود ندارد. `admissionEnabled:false` پذیرش تازه را متوقف می‌کند، ولی وضعیت با همان کد/کلید و مدیریت نگهداری با سیاست معتبر و اپراتور فعلی ادامه دارد. سیاست منقضی یا ناموجود وضعیت قبلی را پاک نمی‌کند؛ تغییر اپراتور، نقش، سیاست، نسخه یا زمان باعث توقف امن عملیات غیرمجاز می‌شود.

دفتر مهمان در فضای جداگانهٔ `guest-rights/v1` است و دفتر RI2 حساب تغییر نمی‌کند. قفل نویسنده، فایل خصوصی بدون دنبال‌کردن پیوند، نوشتن اتمی و ساعت پایدار حفظ می‌شود. سقف ظرفیت یا گزارش پر باعث حذف شواهد حل‌نشده نمی‌شود. شمارندهٔ پذیرش با راه‌اندازی دوباره صفر نمی‌شود. هیچ درخواست حل‌نشده‌ای خودکار پاک نمی‌شود و زمان‌بند اضافه نشده است.

حد نگهداری گزارش هنگام دریافت و حد سابقهٔ پایانی هنگام بستن ثبت می‌شود. سیاست کوتاه‌تر آن‌ها را خودکار کم نمی‌کند؛ فقط بازبینی صریح اپراتور فعلی با CAS می‌تواند آن‌ها را دوباره محاسبه کند. پاک‌سازی فقط برای درخواست بسته‌شده بدون انجام آن و پس از هر دو حد مجاز است. چکیدهٔ کد، شماره، نسخه و اطلاعات حداقلی جلوگیری از تکرار تا پایان بازه می‌ماند؛ کد درست در این مدت410 و کد نادرست404 می‌گیرد و پس از پایان بازه404 می‌شود. پایان این بازه از مهلت رسیدهای قبلی یا مهلت کامل رسید تازهٔ پاک‌سازی از زمان واقعی پاک‌سازی کوتاه‌تر نمی‌شود. این پاک‌سازی دادهٔ حساب/ارائه‌دهنده/پشتیبان را حذف نمی‌کند.

دفتر به کلید فعلی مقید است. کلید جدید یا گم‌شده نباید دفتر را خالی/صفر کند؛ بازیابی خودکار یا چرخش کلید پیاده نشده است. بازگشت نسخه باید سرویس سازگار GI1 و همان دفتر، ساعت و کلید را برای وضعیت و نگهداری حفظ کند؛ دفتر قدیمی بازیابی نشود و نشانگرها حذف نشوند. فعال‌سازی عمومی، تأیید هویت و نماینده، انجام حقوق قانونی، ایمیل/ارائه‌دهنده و دادهٔ واقعی خارج از این نسخه‌اند.

در آزمون ساخت CI، شناسهٔ BUILD_ID ریشه و نسخهٔ مستقل باید برابر باشد. در نبود studio-release.json فقط اتصال ساخت به نسخه و درخت Git با برچسب صریح ثبت می‌شود؛ این روش نه مانیفست انتشار می‌سازد و نه مجوز نصب می‌دهد. مسیر شواهد و محیط‌های آزمایشی با GUEST_EVIDENCE_DIR و GUEST_RUNTIME_DIR قابل نگهداری است.

مبدأ عمومی قابل اعتماد از STUDIO_WEBAPP_URL سرور با نشانی HTTPS و مسیر /studio تعیین می‌شود؛ فقط محیط محلی لوپ‌بک می‌تواند HTTP باشد. تنظیم نامعتبر باعث توقف امن می‌شود و سرآیند Host یا سرآیندهای پراکسی مرجع اعتماد نیستند. مبدأ دقیق و منع درخواست cross-site حفظ شده است.
