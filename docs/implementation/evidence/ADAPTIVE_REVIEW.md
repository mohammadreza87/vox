## Scope and current disposition

This review covers the account-profile persistence service/repository/storage/config/HTTP boundary; Decisions, observation, notifications, personalization and improvement libraries; the new experience orchestrator; Studio runtime/service/HTTP integration; and the Privacy, Shared memories and Experience screens/clients/copy. It also covers the explicit shared-container service/repository/HTTP path and its runtime context projection. Production code and authored tests were read-only. Reviewer-owned files are this report and `src/lib/adaptive/__tests__/delivery-security.test.ts`.

**Accepted for the bounded local, synthetic source scope below.** All independently reproduced defects in this report are remediated on the fingerprinted candidate; no unresolved local regression is waived. Acceptance covers default-off policy, account/space/exact-recipient isolation, explicit agent grants, bounded context, staged shared publication, durable source erasure/replay guards and the tested asynchronous response boundaries. It is not runtime, CI, deployed database, live audience or legal acceptance, and does not accept the entire backlog or a release target.

All examples are synthetic. Providers, Telegram transport and LLM answers were scripted. No live private data, provider inference, external messages or deployment were used. Public official OpenAI documentation was read to check the Decisions wire contract.

## Verified boundaries

- Without a server release manifest, confirmation and a self-declared jurisdiction do not enable optional purposes or explicit saved memory.
- Personalization consent and owning/creating an agent do not infer its private-memory grant. Only an explicit per-space grant permits context; revocation removes it.
- Private context is isolated by account and Work/Personal space. Another authenticated account does not inherit saved notes or grants.
- Explicit saved-memory deletion removes persisted text, retains a deletion marker, survives a new repository instance and prevents replay of the original create-event ID from restoring content.
- Presentation receipts are server-issued and bound to purpose, space, current permission revision, binding revision, locale and notice hash. Revision checks and file transactions support concurrent local-store safety. This is not a proof of deployed Firestore/IAM behavior or all-person legal consent.
- Decisions authorizes before loading minimized input, rechecks before export and before result use, and drops a revoked late result. Its local string-choice/predicate/score subset agrees with the [official guide](https://developers.openai.com/api/docs/guides/decisions) and [create reference](https://developers.openai.com/api/reference/resources/decisions/methods/create), checked on the review date. Model, named answers, distributions, confidence and score arithmetic are compatible. SDK fetch was mocked; account availability, billed usage, actual latency and retention remain unverified.
- Notification preparation returns generic text and an opaque reference, and rechecks source authorization after eligibility. The library has no actual sender or durable scheduler; a plan is not delivered work.
- Preference resolution is confined to a fixed, low-risk schema and exact person/agent/container/space, with explicit choices/reset preceding hypotheses. The library delegates durable reset tombstones, CAS and final-use authorization to its caller.
- Shared selected recipients require confirmed eligible active accounts; workspace ownership/admin rank does not grant content access. Authored sharing creates an independent explicit source. Each participant still needs their own personalization permission for model use, plus explicit container agent access. The positive canary reaches selected Bob's DM and remains absent from the equally eligible workspace owner's model request.
- Shared publication is staged and invisible until exact operation/content/author/recipient/container-intent seals, current authority and actual deadlines pass the final guarded transaction. Independent expiry and author deferred-reader/failure/restart/byte-erasure tests pass. Author/owner deletion and participant departure erase the described source bytes; owner departure erases the container. This does not prove backup/provider purge or a distributed authority lease.
- Group runtime uses metadata-only private policy reads and a separate exact audience shared read; observed membership changes increment epochs, unknown statuses fail closed as guests, and leave/rejoin invalidates observed history. `chat_member` events are requested and handled, but receiving some events does not establish a complete live roster or reliable event delivery.
- Adaptive prompt context is selected only after authorization, at most 12 complete records and 8192 serialized UTF-8 bytes. The lexical ranker never creates access, never truncates individual facts and does not narrow full source/policy invalidation stamps.
- Shared removal/leave UI states the authored-note deletion consequence, and owner leave states whole-container erasure, in EN/FA before confirmation. Experience UI distinguishes authenticated private inbox from external delivery, leaves optional permissions separate and does not label response completion as task success. These are source/unit-test observations, not independent browser/device/accessibility proof.
- Experience orchestration keeps prediction text ephemeral, requires explicit provider enablement and a current profile/core eligibility/agent grant, uses fixed semantic questions, budgets prediction leases and compares fresh authority after provider work. Its observations contain bounded statuses/durations, with task success unavailable. The separate seven-case runtime author suite was independently run and passed; this is source/local evidence only.
- Improvement readiness is read-only and requires independent trusted receipts plus human approval. Its path guard is defense in depth; it is not an enforced process/IAM sandbox or proof that declared changed paths match the artifact.

## Required evidence boundaries and remaining gates

The runtime explicitly denies legacy automatic-memory/history use rather than treating a new profile confirmation as permission to import old stores. Stored optional permission state does not prove that a producer, worker or collection feature is implemented. The actual runtime constructs the adaptive service; constructor-only legacy fallback in synthetic callers must not be interpreted as an approved production mode.

Account profile confirmation is limited to the authenticated account. It is not biometric identity, another person's authentication or implemented shared-account person switching. Work organization permissions and physical bystanders are not established by this account-profile slice.

Live Telegram participant freshness/completeness, cross-store authority atomicity, database/IAM isolation, backup restore/tombstone replay, provider residual deletion, distributed cancellation and reservations, outbox consumers, purge SLOs and production load remain distinct integration/release gates. A check immediately before an external send is not atomic with that send, and cannot recall already transmitted content.

Formal legal review, registered Joyixir entity/address/privacy contact, lawful-purpose inventory, approved jurisdiction/provider/configuration records, retention decisions, participant-facing notices and voice-specific gates remain launch requirements. They do not block synthetic local engineering. No notice, local test or filtered prompt alone establishes their completion.
