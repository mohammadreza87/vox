# Connections broker operations

The broker is an implementation with synthetic evidence. Production bootstrap independently admits read effects only; write/send/destructive/privileged execution is hard-disabled until external audience and source-flow rights are independently qualified. No production credential, OAuth app, provider account, worker identity, callback route or deployment is configured by this change.

Run `node --import tsx scripts/connections-broker.mjs check-config /absolute/private/config.json` under the broker's dedicated non-root OS user before `serve`. The broker UID must differ from Studio's UID. The 0700 vault directory and 0600 config/AES/HMAC key files must belong to that broker user; AES and HMAC keys must differ. Keys are 64 hexadecimal characters representing 32 random bytes. Generate them only on the authorized server. Studio needs a distinct private copy of the HMAC authentication key, with its own ownership and permissions; it must never receive the vault key or vault directory access. Do not inherit Studio/Firebase/Telegram credentials into this process. Startup rejects same-UID operation and known ambient Studio secret variables. Actual OS/IAM separation must be verified on the target.

`brokerConfigurationSchema` in `broker/bootstrap.ts` is authoritative. Set a loopback-only host, port, broker/studio UIDs, private vault/config/key paths, key version, loopback Studio origin, enabled provider IDs, OAuth app profiles, operator scope ceilings and `connectionsManifestFile`. Mirror the operator-owned non-secret Studio manifest to the broker, preserving exact account/space/profile/resource ordering. The broker rebuilds the same account-and-space catalog on each boundary and constructs a correspondingly scoped adapter executor; inventories are never pooled across tenants. Verified identity must match the exact profile subject/tenant. Credential/resource fingerprints remain explicitly credential-bound evidence and do not claim a provider person/project identity.

Private requests use HMAC-SHA256 over timestamp, nonce, method, exact path and body hash, with a 60-second skew limit, one-use nonce and bounded body. Private routes are `/v1/enrollments`, `/v1/enrollments/claim`, `/v1/enrollments/cancel`, `/v1/execute`, `/v1/revoke` and `/v1/invalidate`. Studio's separately authenticated `/api/connections/broker` accepts only strict control actions. Do not expose private routes through a public proxy or log request URLs, bodies, headers, provider responses or callback query strings. Loopback HTTP depends on the actual host/user boundary; cross-host use requires an independently reviewed TLS/mTLS transport.

Only explicitly pinned registered HTTPS OAuth callbacks are admitted. GitHub user OAuth and Google's OpenID-backed services use authorization code, S256 PKCE and random single-use state bound to the current person, binding revision, connection revision and Work/Personal space. Callback processing rechecks authority before exchange and before sealing. It does not connect the account. The user must return to authenticated Studio and claim the sealed candidate. Wrong account, changed binding, stale connection, issuer mismatch, cancellation, expiry or replay denies. A crash after successful control-plane completion converges only after exact verified subject/tenant/issuer and active credential checks. GitHub App installation and provider-specific OAuth variants remain separately qualified; a user token never impersonates an installation.

Static tokens are enrolled only with `enroll /private/config.json <account-id> <work|personal> <flow-id>`, supplied through stdin from a protected operator source. No browser or HTTP endpoint accepts tokens. The broker verifies the provider's native identity (or explicitly admitted resource/delegation profile), seals it and waits for authenticated Studio claim. Operator-asserted scope ceilings are distinct from provider-verified OAuth scopes and write capability. Identity verification is not evidence of resource/write permission. Unsupported identities, worker attestations, missing scopes and unqualified profiles remain unavailable.

The vault uses AES-256-GCM with random IV, key version and authenticated account/person/space/connection/provider/kind/record metadata. Credentials and PKCE verifiers are encrypted in separate normalized files. Rotation/refresh uses a cross-process vault lock and persists `refreshing` before contacting the provider. Failed, ambiguous, expanded-scope or changed-identity refresh leaves the credential inactive and requires reconnect; old refresh tokens are never blindly reused. A fresh lifecycle/binding/revision check precedes activation of a rotated token. Revocation cancels staged flows, aborts active connection signals and deletes local active credentials; provider-side revocation is reported separately as verified/unavailable. Grant-only invalidation aborts only that grant's active calls and preserves independently granted connection use.

Consequential dispatch commits a fenced sending state before provider transmission. Every result is checked against current policy before source registration and again before it crosses back to Studio. The broker returns `committed` for a successful normalized API result; provider/device verification is separate. A possibly transmitted failure returns unknown, without automatic redispatch. Known preflight failures before transmission produce a terminal failed receipt and purge payloads. An already transmitted effect cannot be promised stopped by local cancellation. Root control-plane invalidation remains authoritative even when broker cleanup is temporarily unavailable.

For GitHub/Slack events, `subscribe` uses the same CLI and takes the subscription metadata as its final JSON argument while reading the signing secret from stdin. The secret is sealed only in the vault. Expose only `/webhooks/github/<subscription-id>` or `/webhooks/slack/<subscription-id>` through a reviewed HTTPS proxy preserving exact raw bytes and signature headers. Event verification runs before JSON interpretation. Subscription metadata, external tenant/resource IDs, secret version, replay digest and event type must match. The durable inbox contains minimized receipt metadata only. Event bodies neither grant authority nor create automations. Native readback is required before a separately reviewed event workflow acts.

Recovery: run the control-plane operation recovery sweep and explicit workflow drain under their authenticated account/scope. Never reconstruct ephemeral payloads after process loss. Unknown operations remain held for provider receipt reconciliation; no fresh-key retry, arbitrary browser or shell fallback is permitted. Broker locks left after a crash fail closed; inspect the owning process/provider state before removing any lock.

Rotation/restore: stop new dispatch, preserve current revocation tombstones and unknown-operation ledger, and reconcile active effects. Re-encrypt into a new private vault directory with new key/version while stopped; validate every authenticated envelope with old binding and every new envelope with the new key, then atomically switch protected configuration. Keep the old key only under the approved rollback/backup policy and never restore an older active credential or replay tombstone over newer revocation state. This migration procedure and filesystem ownership require an actual target drill before enabling credentials; the implementation does not claim an executed rotation/restore drill.

Remaining release evidence includes target IAM/UID/proxy isolation, installed runtime artifact, OAuth provider/app review, actual subject/scope/resource/write checks, server-side client deny rules, secret/refresh/revoke/rotation/backup drills, current source suppression across all memory/cache/history destinations, real provider receipts and real Telegram/device journeys. No local fixture substitutes for these checks.

Primary protocol references: [GitHub OAuth authorization and PKCE](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps), [Google server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [GitHub webhook signature verification](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), [Slack request verification](https://docs.slack.dev/authentication/verifying-requests-from-slack/).

Guarded worker enrollment is available with optional `runnerAdmissionFile` and CLI `enroll-runner <private-config> <account-id> <work|personal> <flow-id>`. The strict broker-owned configuration and root-owned read-only Ed25519 verification key validate an expiring signed release attestation bound to exact person/scope, service identity, immutable image, seccomp hash and finite URL/host/service inventory. Enrollment stores a local service-binding marker, not a target bearer/OAuth credential; Studio still requires a fresh authenticated claim. Runtime checks inspect the immutable image and policy bytes and recheck the durable sending lease/current scope before every read boundary. Missing/invalid attestation stays unavailable. No target signer, service identity or SSH host was configured by this work.
