# Connections workflow and event operations

Implementation is qualified with synthetic accounts, injected provider transport, explicit worker drains and normalized file restart tests. No recurring job, provider subscription, external recipient, account credential or live worker was enabled.

`ConnectionsWorkflowService` wraps the existing Connections service/repository. Author a bounded draft with exact account/person/Work or Personal scope, agent, connection and grant; a code-owned versioned runtime skill; up to five fixed read steps; a schedule and IANA timezone; optional quiet hours; an expiry no later than the current grant/person binding; and positive maximum runs/calls. Fixed step arguments permit only schema-validated bounded selection metadata. Free query/content/prompt/body/URL/header/token fields are rejected so source-derived content is not incidentally persisted as workflow configuration. No result text or summary enters the workflow store.

Activation requires the current verified person to review the exact immutable digest and revision. A new connection, agent, audience, source, template, tool/schema/catalog, grant or binding cannot inherit approval. This implementation admits read steps only. External writes, messages, scheduled sends, dynamic recipients and proactive Telegram delivery remain unavailable until independent action/recipient/data-flow qualification. A read grant and an installed provider subscription do not create a workflow.

Schedules support an explicit interval of at least 15 minutes, or one local time each day. Daily occurrences use one local calendar-date key across a fall-back clock fold; a missing spring-forward local time is skipped. Intervals consider the current slot only and never generate a catch-up burst. Quiet hours suppress execution and do not create queued unsolicited delivery. Unchanged/non-actionable work stays quiet. The drain returns only minimized status/receipt references.

`drain(actor,{space,maxOccurrences})` is an explicit worker API, bounded to ten occurrences. It reserves workflow run/call capacity and stable occurrence IDs transactionally, then uses the shared operation ledger with a deterministic UUID for each step and ephemeral arguments. Every provider operation is bound to the active workflow revision, occurrence lease and current policy. Pause, expiry, agent removal, binding change, grant revoke and schema drift stop new dispatch. Interrupted occurrences become skipped/unknown rather than reconstructing payloads and blindly repeating work. Already transmitted provider effects are separately unknown; this read-only implementation does not claim remote cancellation from a local state change.

Run an authorized worker explicitly with `node --import tsx scripts/connections-broker.mjs drain /absolute/private/broker-config.json`. It enumerates only qualified account/space profiles in the mirrored manifest and signs `drainWorkflows` requests to the strict Studio broker-control endpoint. No hidden cron or operating-system scheduler is installed. The application dispatcher must enforce the current per-provider kill switch and daily tool-call budget centrally, including workflow calls; model budgets are separate. Workflow limits additionally bound each reviewed standing rule. Configure an actual recurring worker only within a separately authorized target deployment.

GitHub and Slack ingress is broker-owned. An operator enrolls a signing secret through stdin using the broker `subscribe` CLI; the app stores only an opaque secret reference. The provider callback URL is `/webhooks/<github|slack>/<subscription-id>`, not a credential. Pin the exact provider tenant, native resource ID, Vox resource ID, event types, key version and expiry. The subscription belongs to one current connection/person/scope and creates no agent grant or automation. Protect the broker filesystem, provider hook configuration and public reverse proxy separately.

The broker verifies the original bounded raw bytes before JSON interpretation. GitHub uses `X-Hub-Signature-256` and supported issue/PR/push native resource metadata; Slack uses its versioned raw-body signature and a five-minute timestamp window. Both require exact subscription tenant/resource/type and signed occurrence freshness. A keyed raw-body replay digest persists with the provider delivery ID, so changing an unsigned delivery header cannot replay the same GitHub body under a new ID. Wrong tenant, missing/invalid signature, stale timestamps, bot feedback, unknown event types and revoked subscriptions deny. No raw event body, message text, page content or secret enters the durable inbox/audit.

Signed event acceptance is durable and deduplicated before acknowledgment. It records only receipt ID, subscription, provider/native scope, type, timestamps, key version and keyed replay digest. Event ordering and payload descriptions never become permission or current-state proof. Events cannot trigger another event or create a rule from installation metadata. Newly reviewed workflows do not consume earlier dated event history implicitly.

An event workflow requires a compatible first reviewed native read: GitHub repository identity or Slack channel identity. That exact scoped read runs through the operation ledger and provider adapter. The broker constructs native evidence from the provider's normalized repository/channel ID, provider tenant and source revision. The workflow checks the exact subscribed native/resource identities before any later step, then discards the private result body. A separately injected independently authorized readback may supply equivalent evidence. Missing/mismatched native proof fails the occurrence. Provider event text cannot authorize an action or override this check.

Root integration uses `dispatchBrokerControl(service,input,{workflows})` for signed worker drain. The same strict control dispatcher accepts broker-only subscription registration and minimized verified-event ingestion. Browser HTTP routes expose draft/review/pause/status commands, never signing secrets or raw event data. Shared/group and cross-agent contexts remain unavailable without explicit audience authority. Provider writes are disabled independently in both Studio and the production broker.

Retention and recovery remain explicit. Normalized workflow/event/occurrence records carry retention metadata; deletion and physical TTL jobs must preserve minimal replay fences. The current implementation retains those minimized fences rather than allowing old events to resurrect. Vault/Firestore/filesystem retention, a real recurring worker, provider hook delivery/retry behavior, native callback signatures, target UID/IAM isolation and actual provider/device journeys require deployment/account evidence. A test fixture does not establish these conditions.
