## 1. Starting point and authority

The reviewed source has Studio member/agent access checks in [`permissions.ts`](../../src/lib/studio/permissions.ts), server verification of Telegram Mini App identity in [`auth.ts`](../../src/lib/studio/auth.ts), encrypted bot tokens in [`crypto.ts`](../../src/lib/studio/crypto.ts), and audience checks for memory/history in [`visibility.ts`](../../src/lib/tireh/memory/visibility.ts). These are foundations, not proof of a connector vault, sandbox, egress policy, provider permission contract or production isolation. In particular, Studio admins' ability to use/manage an agent must not become access to its creator's connected account or private data. A bot-token ciphertext protected by one application secret is not evidence of per-connector key isolation or rotation.

Use three separate objects: a **provider account** identifies the verified external account/installation; a **connection** binds a scoped credential reference and reviewed endpoint/adapter; a **grant** authorizes a named Vox agent in an exact tenant, space, container and audience to use specified tools, resources and actions until an expiry/revision. Account ownership, provider permissions, Studio administration, agent use, memory sharing and action approval are separate authorities. None implies the others. Connecting an account starts with no agent grants. A successor, duplicate, imported or rehired agent inherits no grants automatically.

The human credential owner or an explicitly authorized organizational custodian may connect/revoke a credential. The custodian's authority to delegate a service account must be recorded separately from an individual's consent and private data rights. A workspace owner may suspend risky connections; that does not entitle them to decrypt personal credentials or inspect connected content. Sharing a connection must never expose credential bytes. If provider permissions cannot restrict the requested resource adequately, the product must disclose that limitation and keep the adapter unavailable until a narrower credential or reviewed broker exists.

## 2. Threat model and trust boundaries

Protected assets include access/refresh tokens, API/SSH keys, browser cookies, provider account identities, private tool results, hidden resource existence, action drafts and receipts, source-linked memories/derivatives, audit integrity, runtime and evaluator credentials, and provider budgets. Threat actors include a malicious custom server or dependency, compromised provider content, a guest or tenant member, an agent tricked by prompt injection, a stolen session, an overprivileged worker and a mistaken authorized user. Assume remote content and schemas can be hostile, tool annotations can lie, and a legitimate read operation can transmit sensitive input.

| Boundary | Concrete threat | Required control and evidence |
|---|---|---|
| User → Studio | Forged identity, stale approval, account substitution during OAuth | Server authentication, short lived flow state, verified external subject/tenant, exact callback binding; independent identity tests |
| Studio → policy broker → executor | Agent edits a resource ID, impersonates another agent or bypasses UI | Code-owned authorization on every call; executor accepts broker-issued capability only; no model-held credentials or direct network bypass |
| Executor → provider/custom MCP | SSRF, malicious redirects, token theft, excessive scope, hidden writes | Reviewed adapter and egress policy, credential injection only at destination, operation/resource validation, limits and outbound capture |
| Provider/tool result → model | Schema/result injection, fake approvals, injected links, oversized or recursive content | Untrusted-data treatment; bounds, provenance and data labels; content cannot change policy, grants, tool inventory or approval state |
| Private source → other connector/output | Exfiltration through search text, URL/header, message, browser navigation or SSH command | Destination/purpose/recipient authorization for **all** transmitted fields before sending; source lineage and restrictive derived labels |
| Queue/cache/history → resumed task | Revoked grants, changed group, fired agent, stale result/retry | Monotonic epochs, fresh authorization at use/commit/delivery, cancellation and tombstones; replay/concurrency tests |
| Developer → evaluator/release | Author changes oracle or self-approves candidate | Protected independent fixtures/runner/release identities and artifact digest; absent isolation remains a blocking gate |

The product must enforce these controls in services and infrastructure. Prompt text, a skill file, a model's refusal, separate agent names or a Docker label alone provides no security boundary.

## 3. Deterministic call and data-flow contract

**CONN-SEC-01 — Deny by default.** At planning time, before credential release, immediately before provider transmission, before each continuation, before durable writes and before user delivery, evaluate the current verified actor, tenant/space, agent identity/status, task purpose, provider account, connection health/revision, grant, action/resource allowlist, recipient/audience, expiry and policy epoch. Missing/unavailable policy state denies execution. Group knowledge is not provider account access; provider access is not permission to publish its results to that group. Public agents and guests receive no private connection authority by default.

**CONN-SEC-02 — Separate authorization and disclosure.** The broker checks both `mayCall(tool, exact resources/action)` and `mayDisclose(all input sources, destination, purpose, recipients)`. Egress includes body, query/path, URL, headers, tool/schema mirrors, attachments, filenames, trace baggage and continuation state. Example: a private Gmail result includes `PRIVATE_CANARY`; a subsequent public weather/search tool query containing that value must be refused **before any network call**, even when the second tool is marked read-only and its account is authorized. A query about a private repository name can also disclose its existence. Use minimal approved projections or ask for specific sharing approval when permissible. Encoding, translation, paraphrase, aggregate counts, inferred hints and generated summaries do not remove restrictions.

**CONN-SEC-03 — Labels survive derivation.** Results carry source connector/account/resource IDs, source/permission revision, space/container, allowed audiences/agents/purposes, sensitivity, retention and lineage. Combining results takes the intersection of allowed uses and recipients; it never broadens them. Apply the same policy before model/reranker/delegated-agent exposure, durable memory extraction, cache reuse, summaries, embeddings, observability and export. If the runtime cannot safely enforce destination constraints on a mixed-context task, isolate it to the authorized context or refuse that workflow; a model classifier alone is insufficient.

The broker conservatively assigns every model-generated argument, output and continuation the intersection of restrictions from **all context visible to that generation**, including history, earlier tool results, resource metadata, instructions and tool descriptions. The model cannot select a smaller provenance set, assert that a phrase was uninfluenced, or declassify by emitting source IDs. To permit narrower egress, start a fresh isolated generation with only an explicitly authorized minimal projection and independently safe task instructions; neither a reformulated prompt in the same conversation nor a model-generated summary removes taint. Stateless deterministic templates may bind reviewed inputs under their own code-owned data-flow contract. Private canary string matching is only defense in depth; paraphrases and indirect inference remain restricted.

**CONN-SEC-04 — Current audience.** Use an explicit recipient set/history rule and audience epoch, including guests and unknown readers. Every intended recipient must be authorized for all source material. Adding a group member, leaving/rejoining, switching Work/Personal, selecting another account, changing channel or receiving an unknown listener invalidates pending restricted context and output. Clear unsent buffers and rebuild; already delivered text/audio and external copies cannot be recalled. A grant to read data privately cannot be exercised in a group merely because the same person requested it there.

**CONN-SEC-05 — Revocation and memory.** Revoke atomically, increment connection/grant epochs and issue invalidation before acknowledging global completion. Cancel queued/in-flight tasks, credential leases, active streams and browser/SSH sessions; recheck at each side-effect boundary. Suppress connected results and dependent memory/history/summary/vector/cache entries immediately, then purge by the documented retention contract. Retain minimal protected tombstones so retries, source resync or backup restore cannot relearn deleted data. Keep separately justified audit records minimized. Disconnection, grant removal, source deletion and provider revocation have separate UI receipts: future use stopped, provider revocation pending/verified, purge pending/completed, and backup/provider expiry. Do not claim to erase provider-side or previously delivered copies without evidence.

## 4. Protocol, authentication and credential handling

Research was checked against official sources on 19 October 2026. Pin a supported protocol/SDK combination during implementation; current `latest` resolves to **MCP 2026-07-28**. Its HTTP authorization profile requires protected-resource discovery, resource indicators and audience validation, and now records/validates the authorization issuer before code exchange. DCR is deprecated compatibility. These requirements are protocol facts, not evidence that any proposed Vox adapter implements them. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

**CONN-SEC-06 — OAuth profile.** Use authorization code with PKCE S256, cryptographic single-use expiring state tied to authenticated user/session, provider account attempt, connection/agent intent and exact redirect URI. Record authentic issuer, client, verifier and resource server before leaving Studio. Validate returned issuer with exact comparison according to the selected profile before transmitting the code; reject mismatch, missing advertised issuer, reused state, mismatched initiating user or account substitution. Do not trust an error URL from a mismatched issuer. Use pre-registration/client metadata according to the reviewed profile; never accept arbitrary client-registration fields from tool output. OAuth 2.1 remains an IETF draft (the current tracker reports draft 16); RFC 9700 is the published security BCP. Public-client refresh credentials require sender constraint or rotation; prefer supported sender constraints and short access-token lifetimes. Reject implicit/password grants and PKCE downgrade. [OAuth 2.1 draft status](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/), [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)

**CONN-SEC-07 — Audience and scope.** Include the exact MCP `resource` in authorization and token requests. Send only a token issued for the reviewed resource server; validate issuer/audience/signature/expiry through the supported JWT or introspection contract rather than assuming opaque tokens are JWTs. Provider/API credentials remain separate from MCP-facing tokens. Do not forward a user's general provider token through an arbitrary MCP server or accept one intended for another audience. Token passthrough is forbidden by MCP; the design instead uses an explicitly configured, independently authorized downstream credential held by the broker. [MCP authorization and token handling](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

Provider consent describes the actual requested scopes and account. Verify granted scopes/installation resources through documented provider responses/probes; neither a successful OAuth callback nor a green connectivity check establishes all tool capabilities. Maintain `requested`, `granted`, `verified` and `usable-by-this-grant` separately. Insufficient scope becomes a bounded explicit step-up flow showing the added capability and purpose, with cancellation returning to the old grant. Never auto-expand because a server sends a new scope challenge; a broader challenge is a request to assess, not human consent. Do not request an unreviewed whole scope catalogue by default. Provider-specific OAuth profiles may differ from MCP and need their own conformance tests.

**CONN-SEC-08 — Vault.** Store credentials in an access-controlled server-side vault with envelope encryption/KMS, key versioning, rotation, least-privilege workload identities and audited decrypt. Bind authenticated encryption context and lookup authorization to tenant/account/connection; ciphertext swapping must fail. Executors receive short-lived restricted handles/leases; the model, client, logs, traces, database exports and evaluators never receive reusable secrets. Inject credentials only after destination and policy checks. Refresh under a fenced per-connection lock with atomic token-version updates; handle rotation/replay failure by disabling and reconnecting, never falling back to a wider credential. Encrypt backups, control restore, expire caches and verify key rotation/recovery. Credentials pasted into ordinary chat are not a supported enrollment path; redact and direct the user to the secure form without storing them as memory.

## 5. Custom MCP, browser, SSH and supply chain

**CONN-SEC-09 — SSRF/egress.** Custom remote MCP is an advanced, explicitly trusted capability with a reviewed endpoint, transport, operator, data destination and tool catalogue. Require HTTPS and certificate validation. Validate all endpoint/discovery/metadata/registration/JWKS/token/image/resource URLs and every redirect against a network policy; deny private, loopback, link-local, metadata, multicast, IPv6/IPv4-mapped and encoded address bypasses. Resolve and validate all addresses, bind validation to actual connection, and enforce egress at the network proxy to defeat DNS rebinding. Public custom MCP workers cannot reach control-plane, vault, databases or local browser/SSH bridges. A needed internal service gets a separately provisioned narrow bridge, never a broad exception. Bound response size, time, redirects, redirects-to-credentials, concurrency and discovery recursion. These product controls respond to MCP's documented SSRF and confused-deputy risks. [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

**CONN-SEC-10 — Untrusted schema/content.** Pin reviewed server identity, endpoint, protocol and normalized tool-schema digest. Names, descriptions, annotations and resources are untrusted data, including claims of read-only or approval. Validate call arguments with a code-owned schema and adapter policy; deny unknown parameters/tools, schema depth/size abuse, remote schema references and arbitrary callback URLs. New/changed schema, `tools/list_changed`, capability, destination, ownership or executable digest quarantines affected tools and invalidates approvals until reviewed. Check collisions and visually confusable names. Disable server sampling/elicitation/roots access by default; any approved continuation gets a separately bounded data/permission check and cannot request passwords/tokens from chat or additional context implicitly. Never use tool output as system instructions or consent evidence. Read-only status comes from reviewed semantics and observed requests; analytics/read endpoints may themselves record or expose arguments.

**CONN-SEC-11 — Transport/logging.** Modern and legacy MCP profiles are separate compatibility targets. The current HTTP transport removed protocol sessions/GET streams and requires matching method/name/version metadata. Treat parameter mirrors (`x-mcp-header`) as egress and logging exposure: validate them, reject unsafe sensitive workflows or unsupported schemas, and redact those headers at every intermediary. Do not silently omit a required mirror while claiming protocol compliance. Close/cancel streams on revocation, but do not represent cancellation as rollback of a committed provider action. [MCP Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

**CONN-SEC-12 — Chrome/browser.** Run each approved account/task in a dedicated ephemeral browser profile/container with bounded origins and download/upload policy. No personal default profile, shared cookie jar, access to other tasks, password manager, local files, DevTools port exposed to arbitrary servers or unrestricted extension install. Cookies are credentials. Validate navigation, form submissions, file selections and network requests against the same action/data-flow gate; page content and screenshots cannot authorize actions. Reauthenticate or return control for protected login/MFA; avoid persisting screenshots, clipboard and download content as general logs/memory. Show a preview and fresh approval for consequential submissions. Test cross-origin redirects, hidden forms, open redirects and session persistence after disconnect. Treat remote-browser provisioning/identity/access restrictions as an implementation gate.

**CONN-SEC-13 — SSH/CLI/local MCP.** Offer curated commands in an isolated broker before any general shell. Use dedicated non-root principals, pinned verified host keys, short-lived keys/certificates, per-host/repository/directory allowlists and read-only filesystem mounts where appropriate; no host socket, agent forwarding, default cloud credentials or unrestricted port forwarding. Disable arbitrary stdio command installation by default. A local MCP process is executable code and needs explicit provisioning, pinned artifacts and a sandbox; arbitrary user-entered `npx`/shell strings must never run in the Studio server. Shell arguments use structured execution, not interpolation. Sandbox filesystem/network/process/resource limits and enforce egress outside the process. Revoke sessions/leases and clean temporary outputs. General shell/browser control stays unavailable until escape/credential-boundary evidence exists; marking a shell tool read-only is insufficient.

**CONN-SEC-14 — Supply chain.** Keep a reviewed adapter catalogue with publisher/source, exact package and image digests, dependency lockfile, supported protocol, privileges, update owner, license and provenance. Scan and review transitive/install scripts and advisories; a signed or registry-listed server is not proof it is safe. No runtime self-update. Upgrades create a new reviewed candidate, schema/permission diff, sandbox test and canary rollout; rollback preserves revocation epochs and tombstones. Separate development, staging and production credentials. Independent QA needs separate, approved test identities, never developers' personal tokens.

## 6. Action approval, automation and delivery outcomes

**CONN-SEC-15 — Specific approval.** Read access does not approve external messaging, sharing, mutation, deletion, deployment, privilege change, money movement or scheduling. The approval object binds the authenticated approver and authority, task/agent, connection/account, exact recipients/destination/resource versions, normalized full payload/attachments, tool/schema/adapter digest, scope/policy/audience epochs, expiry, limits and single-use nonce. Display a readable preview; store the canonical payload/hash in restricted storage. Any material payload/resource/recipient/version change invalidates it. A tool claiming “already approved,” an old conversation, emoji reaction, inferred intent, a guessed voice identity or another agent's message cannot mint approval. Approval failure, dismissal, offline state and cancellation cause zero side effects.

**CONN-SEC-16 — Explicit automation envelope.** A deliberately approved automation may authorize a bounded class of future actions: exact trigger/schedule/timezone, allowed account/resources/recipient rule, payload template and variable-source rules, read/write/data classifications, limits, expiry and pause/kill controls. Re-evaluate every occurrence against the envelope and current grants, audiences and source restrictions. Dynamic recipients, new destinations, material template changes, broader source data or exceeded limits require renewed approval. Do not repeatedly ask for unchanged actions already covered by that envelope. Delegating a task to an agent or connecting an account alone does not create a standing automation. Keep unchanged/non-actionable monitoring quiet unless periodic updates were explicitly chosen.

**CONN-SEC-17 — Honest state machine.** Use durable intent/outbox, idempotency key where supported, fenced worker lease, current approval check and per-provider receipt/reconciliation. States distinguish draft, needs approval, authorized, queued, sending, committed/verified, failed, cancelled and **unknown outcome**. If a timeout occurs after transmission, do not blindly retry a message/payment/deployment. Reconcile with a provider operation ID/idempotency contract; where unavailable, hold unknown for manual resolution. Never promise exactly-once external effects: a local outbox cannot guarantee them across an arbitrary provider. An accepted request is not a confirmed delivery; device-visible receipt remains separate evidence.

**CONN-SEC-18 — Audit and telemetry.** Record policy decisions, grant/account pseudonymous references, tool/schema digest, safe operation class, normalized resource references, approval/epoch IDs, timestamp, latency, result state, idempotency reference and restricted receipt pointer. Do not log raw tokens, cookies, PKCE verifier, initData, private arguments/results, source text, attachments or full URLs. Hashing a low-entropy secret/private value is not anonymization. Use redaction before logging and bounded protected diagnostic capture with retention/access review; secret scanners cover crash dumps, proxy headers, analytics and tracing. Audit grant/revoke/action outcomes unsampled with tamper evidence and a defined outage policy: fail closed for consequential execution when required durable audit cannot be committed. Operational metrics never become permission evidence.

**CONN-SEC-19 — Managed-bot token holders.** An agent bot's creator holds its token. Agent-signed initData is never sufficient for identity confirmation, grants, tasks, provider data, approvals, erasure or disclosure: require Telegram's Ed25519 third-party `signature` (production key, bot-id-prefixed data-check-string) on any agent-signed surface, keep those surfaces read-only or low-value, and put consequential actions behind VoxxBot-signed initData. Assume anything an agent bot sent is readable by its creator (forward/copy by message id) and that its updates can be redirected (webhook or competing poller); detect redirection (`getWebhookInfo`, getUpdates conflicts) and alert, never auto-act.

## 8. Independent evaluation contract

The definitions below are a **test plan**, not results. The implementation author may run them for development, but another evaluator must select additional held-out attacks, execute against a frozen candidate and issue acceptance. Protected fixtures, gates and release credentials must live outside the author's write authority; repository role instructions cannot enforce that separation. If unavailable, report `UNAVAILABLE` and do not certify independence. This document's author cannot be the sole acceptance reviewer for its own plan or later tests.

Use synthetic fixtures: tenants T1/T2; Work/Personal; owner/admin/member/pending/guest/unknown people; private agents A/B and successor A2; two verified external accounts, lookalike account and shared service account; exact recipients `{P,Q}`; groups with overlapping membership/history rules; scoped credentials with narrower and broader provider permissions; malicious remote MCP, browser pages and CLI fixtures. Seed unique private/source/secret canaries, including EN, FA and mixed-language text, paraphrases and encoded forms. Test all outbound network/provider inputs, headers, model prompts, delegation, logs, storage and UI—not only the final answer. Provider tokens in fixtures are synthetic.

## 9. Qualification, metrics and release disposition

1. **Freeze contracts:** architect, UX, privacy and QA agree on grant/action/data-flow schemas, approval semantics, supported provider/protocol matrix, retention and outage policy. Freeze held-out oracle, budgets and thresholds before candidate execution.
2. **E1/E2 qualification:** independent evaluator reviews exact commit plus dirty-diff/path digest if needed; run unit/contract/property, malicious MCP/browser/SSH and real isolated store/queue/rules tests. Any unauthorized outbound disclosure, mutation, credential use or failed revocation fence blocks the affected feature. Passing quality or latency cannot offset it.
3. **E3 provider gate:** only after explicit task authorization, provision minimal real test accounts/credentials in a separate environment with approved data, costs, recipients and cleanup. Verify scopes, revocation, provider receipts and failure semantics against official current endpoints. Record what is untestable; do not infer compatibility from mock HTTP200.
4. **E4/E5 staged gate:** first synthetic deployed read-only canary, then separately approved reversible-write canary. Verify served artifact, provider/account scopes, policies, rules, vault, egress, workers and actual device journey. Use feature/provider/tenant/agent/connection/read/write flags, rate caps and an executor-level emergency stop. Browser/SSH and payments/infrastructure remain independent high-risk gates.
5. **Progressive release/rollback:** independent release owner approves exact artifact/configuration and limited pilot only after gates. Rehearse disconnect, provider revocation outage, queue drain, unknown-operation reconciliation, rollback and secret compromise response. Rollback code without rolling back grants/tombstones; never restore a broader permission set. Restart only after current policy reconciliation and independent evidence.

Proposed metrics, **not measured**: zero observed unauthorized disclosure/calls/effects/secret exposures in the finite blocking suite; proportion of operations with complete policy+approval+outcome evidence; unknown outcomes and reconciliation age; grant-to-revocation propagation and last permitted send times; purge completion by destination; provider verified-scope coverage; token-refresh conflicts; false-positive safe-call denials; successful user tasks; approval cancellation/abandonment; useful latency p50/p95 and provider cost per verified task. Record denominator, language/channel/provider/account profile, candidate, source timestamps, time uncertainty, failure/timeout/unknown/missing counts and actual usage. Product, security and SRE must set numeric latency, expiry, revocation, purge, cost and recovery targets before release qualification; none is asserted achieved here. If reliable invalidation/lease bounds cannot be proved, keep sensitive long-lived workflows off.

The acceptance report identifies author and independent evaluator, exact artifact/configuration, fixture provenance and protected-runner digest, checks with PASS/FAIL/UNAVAILABLE/NOT_RUN, scope/provider/device evidence, sanitized failures, rollback/kill-switch results, legal/provider gates and named next owner. Every feature receives its own go/no-go. This planning deliverable may be accepted as a reviewed plan while all implementation, real-account, device and release gates remain open.
