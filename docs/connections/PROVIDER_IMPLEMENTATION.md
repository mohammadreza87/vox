## Server integration contract

`createConnectionsCatalog({resourceIdsByTool, destinationIds, endpointProfileIds})` accepts only an operator-reviewed per-connection resource inventory and server destination list. Defaults are empty and cannot execute. `validateArguments` uses strict Zod schemas; `mapResources` derives canonical exact targets and requires inventory membership. The ledger must independently intersect those targets with current person/space/audience/agent grants before dispatch and again before delivery. Never populate one catalog from the union of unrelated accounts or spaces.

`listProviderDefinitions()` exposes safe setup text, explicit eligibility/release evidence, finite tools, effect, scope descriptions, resource format and input JSON schema. `ProviderRegistry({catalog,transport}).execute(toolId,args,{credential,operationId,scopeKind,signal})` receives a broker-only credential `{providerId,endpointProfileId,accessToken}`. It returns `{data,resourceIds,providerReceiptRef,resourceRevision,untrustedContent:true,truncated}`. No raw response, token, user directory, request header or provider error body is returned. Grant/identity/vault/receipt durable execution is owned by the platform and broker layers.

Canonical targets fit the existing 200-character ID contract. Gmail recipient resources use `gmailRecipientResource(address)` = `gmail:recipient:` plus base64url of the normalized lowercase exact address; the separately reviewed operation arguments still show the full recipient to the user. Gmail supports simple addresses up to 128 bytes, without display names. Repository resources lowercase owner/name because repository identity is case insensitive. A connection's exact provider profile separately binds region/instance identity.

## Transport and uncertainty

`SafeProviderTransport` uses fixed server endpoint profiles, HTTPS certificate validation and DNS resolution followed by an address-pinned socket lookup. Every returned DNS address must be public; an explicitly registered internal connector instead requires exact operator-provided address pins. It rejects special-use IPv4/IPv6, credentials/profile mismatch, unsafe paths, non-allowlisted headers, redirects, compressed/unbounded/non-JSON responses, and excessive inputs/results. DNS is covered by the overall deadline; a late resolver cannot dispatch after timeout. There are no redirects, automatic retries or alternate provider fallbacks. Internal endpoint registration is a server deployment concern and is not exposed as a user/model input.

All possible effectful dispatch failures, unusable success responses and normalization failures report `ProviderError.outcome = unknown`, preserving duplicate-risk reconciliation. Writes use `reconcile_only`; a provider receipt proves acceptance only. Hetzner's running action is not a completed reboot. No adapter marks a remote effect verified without separate readback. Reads can still disclose input through provider requests; the broker's pre-egress lineage/purpose/audience policy remains mandatory.

## Identity qualification integration

`broker/provider-identity.ts` implements real narrow authentication/identity calls for all 14 API providers. `ProviderIdentityQualifier.identity()` preserves the broker's four-field identity contract; `qualify()` separately records identity kind, actual external-subject/tenant evidence, API-returned scopes, exact verified resource reads, limitations and `writeCapability: unavailable`. User labels and operator-declared subjects never become provider identity proof. Every admission is parsed with a strict finite schema and cloned/frozen before use.

Notion uses the integration bot ID plus **bot.workspace_id**, explicitly documented in the [current official user object](https://developers.notion.com/reference/user), via version-pinned `/v1/users/me`. Missing workspace ID fails; workspace name/owner/email never substitute. GitHub/Forgejo/Google/Figma use current-user endpoints; Slack uses `auth.test` user/team IDs. These user identities do not prove App installation, resource access, plan eligibility or write permissions.

Hetzner has no authenticated Cloud API account/project identity endpoint in this contract. Explicit `credential_resource` admission verifies at most ten registered server IDs, and namespaces the SHA256 credential fingerprint as a **credential-bound profile**, with account/project identity truthfully marked unavailable. GitHub installation-style credentials can likewise be bound to exact reviewed repository reads and returned owner IDs without claiming a native installation ID. Root's mirrored manifest must explicitly select this identity kind; it is not an automatically accepted account identity. Credential rotation changes that fingerprint and requires reviewed rebinding.

PostHog supports either `/api/users/@me/` plus one exact project (requires the documented user/project read scopes), or an explicit credential-bound profile verifying selected insights without requesting broader user access. Region is fixed by the per-connection admission. User impersonation and resource/project substitution deny. Native Gamend qualification checks current returned org, `grant.ownerAdminId`, game/environment membership, grant expiry/revoke, supported MCP version and actual returned scopes/operation restrictions. It exposes no native write through this adapter.

The broker owner wired these profiles through a factory keyed by the exact current account/space/connection; no cross-account inventory union is used. Browser and SSH do not accept fabricated bearer/OAuth identities: they remain unavailable until a separately attested worker service and registered inventory enrollment channel are configured. Two worker profiles/tools now appear separately, bringing the code-owned catalog to **16 profiles / 39 finite tools**, without widening the 14 API-provider evidence.
