# Connections foundation implementation contract

**Status, 20 October 2026:** merged into `develop`; the branch name below is historical.

Candidate: `codex/studio-connections`, base `d8d6766`. Implementation evidence is synthetic. This file supersedes proposed foundation shapes where the exported source differs; it does not admit a provider or production identity.

The server constructs `ConnectionsService(repository, {resolveContext, catalog, now})`. The resolver uses the authenticated account's current verified person binding and exact Work/Personal scope, with current usable agent IDs. Browser scope, provider subjects and Studio roles cannot supply this authority. Only a private one-person audience is currently admitted. Enrollment accepts a provider ID and label, creates a pending connection and zero grants. Only the broker's verified enrollment callback can attach the external subject/tenant/scopes. Reconnect creates a new connection; revoked identifiers and grants cannot be silently reused.

`ConnectionsRepository` validates strict versioned normalized records, partition ownership, unique operation request/idempotency indexes and active connection-agent grants on every transaction. In-memory fixtures serialize transactions and roll back failed mutations. Firestore uses individual server-only collection documents and a transactional partition fence; it does not share `studio/state` or the adaptive account JSON document. File storage uses separate collection/record files, a process-shared lock, fsynced generation directory and an atomically replaced pointer. Reload removes unreferenced crash generations and never restores them. Corrupt pointers/records fail closed. A crashed lock requires operator investigation before removal. Firestore direct-client deny rules and actual broker filesystem/IAM isolation remain deployment evidence, not implications of TypeScript classes.

The browser receives allowlisted connection metadata and operation receipts. Full payload preview is available only to the current verified owner after fresh scope/source checks. Credential handles, tokens, provider subjects and raw provider bodies never enter the list view. All public command parsers are strict Zod objects with bounded arrays/text. Provider tools and argument schemas come from the code-owned catalog. Dynamic resource mapping can be admitted by an empty descriptor resource list only when `mapResources` supplies the exact resource IDs; grants still name exact resources and reviewed destinations.

`propose` is restricted to isolated manual input. The model bridge must call `proposeGenerated(actor, input, {sourceIds, isolated:true})`, passing every source visible anywhere in that generation, including history, summaries, earlier tool results and delegated context. The service unions those trusted labels with declared labels, so omission from generated arguments does not remove taint. Every source and ancestor is checked against the current agent, person binding, connection/grant revision, scope, audience, destination, purpose, expiry and tombstones. Paraphrasing or encoding does not change labels. Unknown/group audiences and unsupported memory persistence deny. `ConnectionsLineage` stores labels, never source bodies. `registerResult` intersects all parent restrictions. No memory authority is inferred from a connection grant; the separate memory bridge is unavailable.

Operations reserve the explicit grant call budget in the same transaction as durable intent, audit and retained dispatch outbox. Equivalent request/idempotency keys converge; a changed canonical argument, target revision, tool/schema/catalog, destination, audience, grant, binding or policy conflicts. Approval binds the exact canonical proposal digest, current approver and binding, expiry and single-use nonce. Worker claim and `markDispatched` re-resolve current authority; the latter consumes approval transactionally before network transmission. Fenced leases reject stale workers and duplicate dispatch. `settle` records the provider outcome; `assertUsable` rechecks independently before any model continuation, source registration, cache/memory use or final delivery. Revoke between dispatch and completion fences late workers and suppresses output.

Retained arguments live in separate protected payload records until terminal completion, cancellation, revocation, deletion or recovery expiry. Ephemeral arguments remain only in the live process registry; durable records contain an opaque lease and digest. They are never placed in a dispatch outbox. Losing them before dispatch expires the operation. Losing a possibly dispatched lease produces `outcome_unknown`; neither mode blindly redispatches an uncertain effect or generates a fresh idempotency key. Read, committed and verified receipts are distinct. Provider reconciliation and compensating/undo actions require independently current rights and provider evidence.

Revocation writes a persistent replay tombstone and invalidation outbox. Source deletion suppresses descendants and dependent operations and purges current payload records. Its receipt remains `purge: pending` until history/memory/cache/index/backup consumers actually acknowledge their own deletion. Provider revocation and backup expiry are separately unverified. No source label, account disconnect or local file deletion claims previously delivered provider copies were erased.

Receipt/audit metadata has an explicit 90-day retention field; retained argument expiry is at most the 15-minute operation deadline. The worker must run lease/deadline recovery and configured physical TTL/purge maintenance. Minimal replay tombstones remain retained to prevent restore/retry resurrection. Firestore emulator/rules, production retention jobs, restore/rotation drills, distributed capacity/load, actual provider scopes and real device delivery remain separate required gates. Transaction capacities fail closed rather than partially revoking; production admission must qualify maximum fanout within those bounds.
